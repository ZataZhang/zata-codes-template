Zata Code Template 架构导览

这是一个供派生项目扩展的模块化单体模板：两个 Web 客户端通过 HTTP 连接 Python 后端，后端以四层边界组织用例与适配器，当前业务示例以 public / admin 双认证域为主。

设计原则分层架构启动装配数据模型生命周期与权限认证业务流程前后端协作扩展到其他场景实施路线
第一部分 · 架构设计

设计原则

模板先把变化边界和依赖方向固定下来，让派生项目按业务域增加能力。

后端按职责分层

api 接入请求，core 编排用例，engines 提供平台能力，infrastructure 对接数据库与外部实现。

组合根集中装配

composition 创建服务、仓库和运行依赖，再注册路由与中间件。业务模块不负责拼装全局对象。

核心依赖抽象契约

仓库、会话存储、密码哈希和沙箱能力以接口表达，具体实现由基础设施提供并注入。

认证编排复用，身份域隔离

两域共用 AuthService 的实现逻辑，各自绑定独立用户表、Cookie 与 Redis key 前缀。

前后端通过 HTTP 解耦

两个 Web 客户端分别构建和部署，只依赖后端 API 契约，不直接导入 Python 模块。

系统分层与边界

图中从上往下读请求运行路径；源码依赖通过 core 契约反转，由 composition root 注入具体实现。

边界职责当前实现位置
客户端页面、路由、会话交互frontend-public/；frontend-admin/

src/backend/composition/ 位于四层之外，负责构建依赖、运行数据库迁移、准备初始账户并装配 FastAPI。两个前端位于后端边界之外；生产环境由各自的部署入口连接后端 API。

核心数据与存储

账号身份、会话状态和对外返回的主体分别承担持久化、登录续期和请求授权职责。

类型关键字段存储与用途
UserAccountid · identifier · display_name · password_hash · is_activePostgreSQL；public 与 admin 分表保存
SessionRecorduser_id · created_at · expires_atRedis JSON 值；token 位于带域前缀的 key 中
AuthenticatedPrincipaluser_id · display_name · identifier · domain请求内主体；不包含密码哈希

存储分工

  1. PostgreSQL 保存用户账号和业务持久化模型。
  2. Redis 保存服务端会话记录；两个认证域使用不同 key 前缀。
  3. bcrypt 将密码转换为哈希后保存，认证成功后返回不含敏感字段的主体。

会话生命周期与访问边界

登录只创建服务端会话；受保护请求重新解析会话并检查账号状态，登出或过期后访问被拒绝。

15 天 · 滑动窗口每次会话解析后续期，具体值来自配置。
60 天 · 绝对上限会话从创建时起有最大存活时间。
2 个认证域Public 与 Admin 分别校验 Cookie、Redis 前缀和用户表。

访问条件交集

每个请求必须落在同一个认证域内，Cookie、Redis 命名空间、用户记录和路由守卫需相互匹配。

访问方身份与登录受保护入口边界
Public邮箱；允许自助注册；session_id/auth/* 与 public 依赖守卫业务资源由派生项目添加；当前模板不内置 public 资源
Admin用户名；启动种子创建；admin_session_id/admin/* 与 admin 依赖守卫可管理 public 用户和查看运行轨迹；不开放注册

禁用账号会在下一次会话解析时失效。当前代码定义 session_id 与 admin_session_id 两个 Cookie；docs/architecture/frontend-architecture.md 中“共享同一个 session_id”的描述与实现不一致。

第二部分 · 业务流程

Public 登录与受保护请求

以 public 用户流程为例，纵向看浏览器、API 核心逻辑与数据存储在每个阶段分别做什么。

  1. 浏览器调用 POST /auth/register 或 POST /auth/login；admin 域只有登录端点。
  2. AuthService 归一化登录标识，查询本域账户，校验密码哈希并检查 is_active。
  3. 认证通过后，Redis 创建本域 Session；API 通过 HttpOnly Cookie 返回 token。
  4. /auth/me 或受保护路由从 Cookie 取 token，续期会话并重新读取账户状态。
  5. 登出删除 Redis 记录并清除 Cookie；会话过期或账号禁用会让后续请求得到 401。
Public 标识邮箱 · public_user · public:session:
Admin 标识用户名 · admin_user · admin:session:
共享实现同一 AuthService 代码，由 composition 分别注入两域依赖

前端与后端如何协作

两个客户端有各自的页面、路由和会话状态，通过 HTTP 契约连接 API；后端认证域决定每次请求的身份范围。

客户端职责请求方式认证边界
frontend-public/官网、注册登录和轻量应用页面开发时直连配置的 API 基址；生产时由 API_BASE_URL 指向后端调用 public 域端点并携带 session_id
frontend-admin/管理员登录、用户管理和运行轨迹诊断Vite 开发代理；生产由 Nginx 反代 /api/*调用 admin 域端点并携带 admin_session_id
src/backend/api/路由、请求校验、响应 DTO 和依赖守卫FastAPI HTTP / MCP不让客户端直接依赖 core 或基础设施模块

页面访问身份由对应 Cookie 和后端守卫确认。部署到同一主机名不会让 public 与 admin 会话互相通用。

扩展到派生项目

新业务从一个可验证的垂直切片开始，沿现有边界添加用例、适配器和 HTTP 契约。

场景新增内容复用边界
增加业务资源core 领域模型与用例、API 路由、数据库模型与迁移认证主体、仓库契约、composition 装配与前端 HTTP 客户端
接入新平台能力定义 core 端口并提供 engines 或 infrastructure 适配器用例编排和 composition 注入方式
增加独立客户端页面、路由、会话交互和 API 适配只依赖后端 HTTP 契约；可按产品需求选择 public 或 admin 域
增加后台运维能力admin API 与对应的管理页面Admin 身份守卫、Admin 用户仓库与观测基础能力

业务模块是派生项目的责任。需要跨层访问数据库或外部服务时，先在 core 中声明端口，再由具体适配器实现，并由 composition root 连接。

实施路线与开工前决策

以下路线用于把模板扩展为具体业务系统；它描述推荐顺序，不代表仓库当前正在实施这些事项。

阶段交付内容完成标志
1 · 明确边界业务实体、数据归属、public/admin 使用范围身份域和资源 owner 可从需求中明确
2 · 定义用例core 模型、业务规则、端口契约用例可由输入与输出描述，不依赖具体 SDK
3 · 接入实现数据库迁移、仓库或平台适配器、composition wiring依赖可装配，运行环境配置有文档
4 · 暴露能力API DTO、路由、前端调用与用户提示沿真实用户入口完成一次端到端流程
5 · 验证与维护测试、架构文档、部署说明和配置示例边界、异常路径与运行参数有证据

实施前需要确定

  1. 资源归属哪个用户域，哪些角色可以读写？
  2. 外部能力失败、超时或不可用时，用例如何返回可处理的结果？
  3. 新增配置是普通参数还是密钥，如何在本地、CI 和生产环境注入？
  4. 用户可见的 HTTP/API 行为如何保持文档、前端和后端契约同步？
