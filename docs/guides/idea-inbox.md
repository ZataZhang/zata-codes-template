# Idea Inbox

本仓库用 `tasks/inbox/` 承接"随手想法"：先留下原话，再由 AI 维护一份总结。
它是任务生命周期的**第 0 阶段**，位于 PRD 之前：

```text
tasks/inbox/        →   tasks/pending/   →   tasks/archive/
随手想法：原话 + 总结      成形的 PRD          已交付的 PRD
```

## 为什么放在 tasks/inbox/

- `tasks/*` 在模板同步里"永不同步"（`scripts/shared/template/sync_template.sh` 的 `_is_never_synced`），所以每个项目的想法天然私有，不会串到其他派生项目。
- PRD 验收 hook 只校验 `tasks/` 根目录和 `tasks/archive/` 下的 PRD 文件（`hooks/shared/check_prd_acceptance_checklist.py`），**不会扫描 `tasks/inbox/`**，因此这里可以自由记录、无需验收清单。
- 想法成熟后用 PRD 流程升级成 `tasks/pending/` 下的正式 PRD，形成闭环。

## 文件职责

inbox 原话、摘要与生命周期状态按职责保存：

| 文件 | 角色 | 谁来写 | 可否改写 |
|---|---|---|---|
| `tasks/inbox/ideas.md` | 原话引用 + 标注的 AI 背景 + 条目状态 | 人（原话）+ AI（背景块） | 原话和背景只追加；标题元数据可更新 |
| `tasks/inbox/summary.md` | AI 总结 | AI | 可随时重写 / 再生 |

想法原话和生命周期标记都记录在 `ideas.md`；`summary.md` 是派生产物，任何时候都可以从 `ideas.md` 重新生成。

### 生命周期状态

想法的有效状态为 `pending`（待处理）、`in_progress`（进行中）、`completed`（已完成）或 `abandoned`（已放弃）。状态标记写在 `ideas.md` 标题中；人工放弃与手动完成分别通过 `<!-- idea-status: abandoned -->` 和 `<!-- idea-status: completed -->` 记录。`Source Idea Refs: <idea-id>, ...` 头部字段将 PRD 关联到原始想法：草稿待审阅、PRD 位于 `tasks/` / `tasks/pending/` / `tasks/hold/` 时为进行中，PRD 移入 `tasks/archive/` 后为已完成。没有关联 PRD 且没有显式状态标记时为待处理。

关联 PRD 通过头部的 `- Source Idea Refs: <idea-id>, ...` 引用想法 ID。草稿生成时自动写入引用；手工创建 PRD 时也应保留该字段。新想法 ID 和状态写入 `ideas.md` 标题；旧条目缺少 ID 时，根据原始内容稳定派生并补进标题。读取快照时，系统根据草稿和 PRD 位置同步状态标记，只更新标题行，不改动原话引用和 AI 背景块。

没有 ID 或 PRD 引用的历史条目默认保留为待处理，不能仅凭创建时间推断其已完成或已放弃。用户可在历史列表逐条标记完成或放弃，或建立明确的 PRD 关联。

`/ideas` 默认只展示待处理与进行中的条目；已完成和已放弃条目通过历史开关查看。放弃或手动完成必须由用户明确指示，不能仅凭想法年代推断。没有 PRD 引用的旧想法也可以在页面手动标记完成。恢复放弃项会将标题状态恢复为 `pending`；如果此时已有 PRD，页面会重新显示从 PRD 推导的状态。

## ideas.md：原话引用 + AI 背景

- 追加式、按时间正序，最新条目追加在文件末尾。
- 每条想法一个二级标题，标题包含时间戳、可选短标签，以及状态 HTML 注释：
  - `## 2026-06-14 18:30 · 部署 (idea-20260614183000-a1b2c3) <!-- idea-status: pending -->`
- 标题下方先是**用户原话的逐字引用**（`>` 引用块）；**不要替用户润色、改写、纠错或精简**。
- 引用块之后可以跟一个**明确标注为 AI 派生**的背景块，记录这次讨论得到的动机、边界、已否定方案与收敛结论。它与引用块严格分开，不得让 AI 归纳读起来像用户原话。
- 文件使用 UTF-8 编码；首次记录时若 `ideas.md` 不存在，直接按本页格式新建。

示例：

```markdown
## 2026-06-14 18:30 · 想法记录机制 <!-- idea-status: pending -->

> 我感觉我会有不断的想法冒出来，想要一个地方记录每一次想法的原话，同时让 AI 做总结。

**AI 派生（非用户原话）**
- 背景/动机：想法零散、易丢，需要一个先收集、后成形的缓冲层。
- 边界/约束：只做 Markdown 文件与读写约定，不引入新命令、服务或 CI。
- 收敛结论：先落 `tasks/inbox/`，成熟后再升级为 PRD。
```

### 给 AI 的硬性规则

**什么时候写（触发规则）**——默认**不写**，不要把对话变成转写稿：

- **用户明确要求**时才写：`记一下`、`记录想法`、`帮我记下来`、`把这个想法记下来`、`capture this idea`，或等价的请求。
- **某个话题收敛到可以开 PRD 的状态**（有明确主张、边界与动机）时，可以追加一条，并且**必须告诉用户**记了什么（时间戳 + 短标签 + 一句话），方便用户改或删。
- 讨论中途的片段、纯问答、讨论中被否掉的方案、闲聊——都**不写**。用户说"别记 / 不用记"就不写，事后也不要再问。

**怎么写**：

- 在 `ideas.md` **末尾追加**一条新条目，时间戳用当前本地时间。
- 为新条目生成稳定的 `idea-<timestamp>-<random>` ID，并附在标题标签中，例如 `## 2026-06-14 18:30 · 部署 (idea-20260614183000-a1b2c3) <!-- idea-status: pending -->`。旧条目缺少 ID 时由解析器稳定派生，并只把 ID 补进标题元数据。
- `>` 引用块必须是用户**自己的措辞**，逐字保留。想法横跨多轮对话时，引用其中承载主张的原话；任何归纳都放进 AI 背景块。**不得编造引用**——没有可引用的用户原话就不要建条目。
- **禁止**改写、合并、删除、重排或"优化"已有条目的原话与 AI 背景块。状态变化只更新 H2 标题中的 HTML 注释；给旧条目补稳定 ID 也只改标题元数据。原话是证据，不是草稿。
- 想法后续演进了就**追加新条目**并引用早先的时间戳，不要回头改写旧条目。
- 只有用户明确表示不再推进时，才把该标题标记改为 `<!-- idea-status: abandoned -->`；新条目默认待处理，不要按年代批量标记已放弃。
- 跨条目的聚类与评论放在 `summary.md`，不要混进 `ideas.md`。
- 一次对话通常一个想法只产出一条，不要把同一个想法拆成多条碎片。

## summary.md：AI 总结

当用户说"总结一下想法 / 整理 inbox"，或在合适时机，AI 读取整份 `ideas.md`，重写 `summary.md`。建议结构：

- **主题聚类**：把零散想法归并到几个主题下，每条标注来源时间戳，便于回溯到原话。
- **可执行候选**：哪些想法已成熟到可以开 PRD，给出建议的优先级 / 类型。
- **待澄清问题**：还需用户拍板或补充信息的点。
- **已升级**：已进入 `tasks/pending/` 的想法，链接到对应 PRD。

`summary.md` 顶部应标明它是 AI 派生、可被重写，事实以 `ideas.md` 为准。新增一条想法后 `summary.md` 即过期，AI 应在确认捕获时说明，并在用户要求时重写。

## 升级为 PRD

当某条想法值得动手时：

1. 用 PRD skill 在 `tasks/pending/` 下创建正式 PRD（命名与规范见 `skills/prd/SKILL.md`）。
2. 在 `summary.md` 的"已升级"区标注该想法对应的 PRD 路径。
3. 在 PRD 头部保留 `- Source Idea Refs: <idea-id>, ...`，使产品页能根据 PRD 草稿 / pending / archive 位置推导想法状态。
4. 原话和 AI 背景保留在 `ideas.md` 不动，作为需求溯源；生命周期状态保存在同一条目的标题元数据中。

## 约定与边界

- 默认单文件 `ideas.md`；体量过大时可按年份滚动归档，例如把往年条目移到 `tasks/inbox/ideas-2025.md`，并在新文件顶部注明衔接。
- 想法内容是项目私有的，不随模板同步传播；新项目通过 `just copy` 只继承空的 `tasks/inbox/` 目录骨架和本约定，不继承任何已有想法。
- 本流程不引入新的命令、服务或 CI；原话 / 总结 / 状态仍由本地文件与读写约定维护。
