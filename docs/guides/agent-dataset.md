# Agent 数据集构建

这是持续演进的数据采集与整理约定。目标是让项目日常开发留下可追溯的需求、尝试、反馈和验收事实，
供后续检索复用、评测或训练。创建 PR 不会自动更新模型参数；数据质量与后续使用方式需要独立建设。

## 任务、尝试与观察

以 **repository + Issue** 表示一个任务，PR 表示交付，提交表示代码版本，评论表示某一时刻的观察。
一次任务可以跨多个 PR，一个 PR 可以有多次修复；提交次数和重试次数都不自动等于有效尝试次数。

例如：

| 时间 | 开发事实 | 整理时的含义 |
|---|---|---|
| 第一次提交 A | 本地测试绿，创建 Draft PR #20 | 已有候选实现，真实效果待验证 |
| 用户试用 A | 原问题仍出现 | A 有明确失败反馈，保留复现方式与代码 SHA |
| 第二次提交 B | 调整方案，仍在 #20 | 同任务下一候选，不覆盖 A 的失败记录 |
| 用户验证 B | 真实入口通过，CI 也通过 | B 是成功候选，须审查证据对应的最终代码 |
| 合并 #20 | 回到默认分支 | 开发交付状态；本身不是成功 oracle |
| 合并后反例 | 发现漏场景，开启 #23 并关联原 Issue | 追加反证，重新评估原成功标签 |

`just ai pr` 用 `pending` / `failed` / `passed` 记录调用方的真实验收观察；自动化 `just test` 是另一项证据。
不要把 Draft、open、merged 与验收状态混成一个字段。人工确认也是观察，记录确认人、时间、入口和版本，
而非笼统写「用户已验收」。具体命令见[对话中的 PR 交付](ai-pr.md)。

## 原始层与整理层

**原始层保留事实，整理层表达判断。**

- 原始层：用户逐字要求及来源、AI 单独整理的任务、补充/纠正、代码起点与每轮 head、验证结果及其限制。
  Issue 原始正文保留任务输入；后续反馈与交付观察追加在评论；PR 正文维护最新概况。
- 本机采集缓存：Git common dir 的 `ai-pr/.../events.jsonl`，用于恢复与原始记录备份，不进项目历史。
  Issue/PR 评论是远端记录，但可被平台用户编辑或删除，仍应定期导出到独立数据集仓库。
- 整理层：将相关 PR 聚合为任务，按代码 head 与反馈划分尝试、去重重试记录、补独立可理解的任务描述，
  再评估是否可用于评测、训练或失败/成功偏好对。始终保留原始来源与整理理由，不能覆盖原始层。

当前命令在**交付时**采集，不是开工前快照。`request_source=conversation` 代表可见对话原话，
`retrospective` 代表事后补述。首次交付时已有代码不能伪装成预先记录的需求；事后从 diff 推断的内容只能
作为 AI 整理，不能标成用户原话。对于评测任务，AI 整理的任务必须描述问题与验收，避免携带实现答案。

## 与 KedaCode 的衔接

相邻 `keda` 项目的 `scripts.dataset_export` 已支持从任意项目的已合并 GitHub PR 采样：

```bash
# 在 keda 仓库运行；目标参数是被采集项目的本地路径。
uv run python -m scripts.dataset_export \
  --github-pr-repo /path/to/project --output samples.jsonl
```

其现有规则优先读取关联 Issue 正文，没有 Issue 则退到 PR 描述。后者可能泄露实现答案，属于弱输入。
`just ai pr` 的 `Closes #N` 使任务输入与代码交付能够关联；这只是采集入口衔接，不保证样本自动合格。

**当前边界**：keda 的既有导出没有专门解析本命令的逐轮 JSON 评论，也不会自动将跨 PR 的修复归并成
失败/成功训练对。普通 PR 来源没有 runner attempts，不能把评论数冒充 runner attempts。
首次 Issue 正文能由现有导出读取，后续反馈、重开任务与逐轮观察需要后续扩展导出器读取评论和本机事件，
并保留 `schema_version`、来源与缺失标记。当前改动不修改相邻仓库。

后续优先级：

1. 先在日常交付中保留可靠记录，人工抽查少量任务，验证原话、代码范围与真实反馈能否对应。
2. 当多轮记录确实积累后，再扩展 keda 导出：抓取评论，按 Issue 聚合多个 PR，归档原始事件，追加整理补丁。
3. 有足够高质量样本后再建设评测与训练闭环，比较固定基线和改进后的 Agent；不要只观察合并率。

## 成功样本与失败/成功对的整理

不能仅凭「合并」「CI 绿」或 AI 自述筛为成功。至少核对原要求、真实入口证据、证据对应版本和后续反例。
没有足够证据就保留 `unverified`；后续反证出现时追加失效记录，重新生成整理视图。

失败/成功对必须来自同一任务和相同验收要求：失败候选 SHA、失败观察与成功候选 SHA、成功证据都可定位，
且能区分方案失败、环境故障与需求变更。不能把缺凭据、CI 没启动或用户新增需求都当作旧方案失败。
从 A 修到 B 不代表所有 A→B 都可直接作偏好对，仍需检查任务输入和验收是否一致。

merge commit 尽量保留开发提交；仓库必须 squash/rebase 时，在原始记录中保留合并前 head 和每轮上下文，
后续导出及时归档对应补丁/树与 GitHub merge commit。SHA 只是定位信息，不保证平台永久保存不可达对象；
当前命令不自动归档代码对象，不自动删除工作分支，也不为整理数据强推或改写历史。

## 数据发布与长期维护

项目仓库保存本页与交付约定，原始日志、大产物及完整会话放独立数据仓库或受控存储。
导出与归档应是确定性工具；语义补全、任务聚合和质量判断允许人工或 Agent 参与，保存来源与判断依据。
发布前人工抽查脱敏与数据授权边界，检查密钥、个人信息及私有业务内容；模式扫描不能保证覆盖所有敏感信息。

不要为了数据整齐删除失败记录、改写用户要求、统一标成功，或把从答案生成的任务当作独立评测输入。
本页随着真实采集经验增量维护，不提前建设训练平台或为每条约定增加程序门禁。
