# 前端 i18n（中英文双语）

本仓库的两个前端都支持中英文双语，但**各自使用与框架匹配的 i18n 方案**，不强行统一成同一个库：

| 前端 | 框架 | i18n 方案 | 模式 | locale 持久化 |
|---|---|---|---|---|
| `frontend-public/` | Next.js App Router | `next-intl` | 服务端（SSR）渲染 | cookie `NEXT_LOCALE` |
| `frontend-admin/` | Vite + React + TanStack Router | `react-i18next` | 客户端渲染 | localStorage `i18nextLng` |

选型理由：Next.js App Router 下 `react-i18next` 缺少一等 SSR 支持，会导致首屏闪烁，且 SEO metadata 无法按 locale 在服务端生成；后台是纯 SPA，客户端检测与缓存已经足够。详见 PRD `tasks/pending/P2-FEAT-20260707-150000-frontend-i18n-bilingual.md` 的 Decision Log。

支持的 locale 集合为 `en` + `zh`，默认 locale 为 **`en`**（决策 D1）。两者都不使用 URL 语言前缀（`/en/...`）。

## 公开站（frontend-public）

### 文件结构

```text
frontend-public/
├── i18n/
│   ├── constants.ts   # LOCALE_COOKIE / SUPPORTED_LOCALES / DEFAULT_LOCALE / isSupportedLocale
│   ├── negotiate.ts   # negotiateAcceptLanguage：zh-*→zh、en-*→en
│   ├── request.ts     # getRequestConfig + getRequestLocale（cookie > Accept-Language > 默认）
│   └── locale.ts      # "use server" setUserLocale：写 NEXT_LOCALE cookie
├── messages/
│   ├── en.json        # 英文文案
│   └── zh.json        # 中文文案
├── components/language-switcher.tsx
├── next.config.ts     # createNextIntlPlugin("./i18n/request.ts") 包裹导出
└── app/layout.tsx     # generateMetadata + <html lang={locale}> + NextIntlClientProvider
```

### locale 协商优先级

1. `NEXT_LOCALE` cookie（用户显式选择过）
2. `Accept-Language` 请求头（按语言主标签归一：`zh-CN`/`zh-Hans` → `zh`，`en-US` → `en`；不支持的语言返回 `null`）
3. `DEFAULT_LOCALE`（`en`）

协商结果决定 SSR 输出的文案与 `<html lang>`，因此首屏就是正确语言，不会闪烁。

### 渲染流

1. 请求到达，`next-intl` 插件调用 `i18n/request.ts` 的 `getRequestConfig`。
2. `getRequestLocale()` 按上面的优先级解析 locale。
3. 动态 `import("../messages/<locale>.json")` 加载文案并返回 `{ locale, messages }`。
4. `app/layout.tsx` 用 `getLocale()` / `getMessages()` 取值，`NextIntlClientProvider` 把 locale 与 messages 注入客户端组件树，`<html lang={locale}>` 跟随。
5. `generateMetadata()` 用 `getTranslations("html")` 产出 `<title>` / `<description>`。

> **注意**：本应用不使用 URL locale 前缀，`next-intl` 插件无法从路由推断语言，因此 `getRequestConfig` 自行读取 cookie 与请求头，忽略插件传入的 `requestLocale`（它只会用 `en` 兜底）。

### 切换器行为

`components/language-switcher.tsx` 是一个客户端组件：

1. 调 `setUserLocale(next)`（server action）写 `NEXT_LOCALE` cookie；
2. 同时用 `document.cookie` 即时写入，保证当前文档无需等待往返；
3. `router.refresh()` 触发服务端重渲染，整页文案随之切换。

### 客户端 / 服务端边界

`i18n/constants.ts` 是**客户端安全**的顶层模块，两端共享常量。任何依赖 `cookies()` / `headers()` / `next/headers` 的代码必须留在 `i18n/request.ts`（只被 next-intl 运行时消费）或 `i18n/locale.ts`（只作为 server action 被消费），**不要从客户端组件 import 这两个模块**，否则会把 `next/headers` 打进浏览器产物。

## 后台（frontend-admin）

### 文件结构

```text
frontend-admin/src/
├── i18n/init.ts               # i18next 初始化 + SUPPORTED_LOCALES / DEFAULT_LOCALE / LOCALE_STORAGE_KEY
├── locales/
│   ├── en.json                # 英文文案
│   └── zh.json                # 中文文案
├── components/language-switcher.tsx
└── main.tsx                   # 组件渲染前 import './i18n/init'
```

### locale 检测优先级

`main.tsx` 在任何组件渲染前执行 `import './i18n/init'`，i18next 用 `i18next-browser-languagedetector` 按以下顺序检测：

1. `localStorage` 的 `i18nextLng`（用户显式选择过）
2. `navigator` 语言
3. `DEFAULT_LOCALE`（`en`）

检测结果会写回 `localStorage`（`detection.caches: ['localStorage']`），所以刷新、重开浏览器后仍保持上次选择。`load: 'languageOnly'` 保证 `zh-CN` 这类带区域的标签能匹配到受支持集合。

### 切换器行为

`components/language-switcher.tsx` 调 `i18n.changeLanguage(next)`；组件通过 `useTranslation()` 订阅语言变化，自动重渲染，无需整页刷新。

### `<html lang>` 同步

`i18n/init.ts` 在初始化完成与每次 `languageChanged` 时把 `document.documentElement.lang` 同步为归一化后的 locale，供屏幕阅读器与端到端测试读取。

## 约定速查

| 契约 | 公开站 | 后台 |
|---|---|---|
| 持久化键 | cookie `NEXT_LOCALE` | localStorage `i18nextLng` |
| 写入方 | server action `setUserLocale` + 切换器的 `document.cookie` | `LanguageDetector` 的 `caches: ['localStorage']` |
| 读取方 | `i18n/request.ts` 的 `getRequestLocale()` | `LanguageDetector` 的 `detection.order` |
| cookie 属性 | `path=/`、`sameSite=lax`、`maxAge=1 年` | 不适用 |
| 切换器 testid | `language-switcher`、`language-option-en`、`language-option-zh` | 同左 |

两端的切换器都提供 `data-testid="language-switcher"` 与 `data-testid="language-option-<locale>"`，端到端测试直接复用这两个选择器。

## 新增文案规范（决策 D3）

- **按命名空间组织**：顶层键是页面 / 领域命名空间，叶子键是 camelCase 的具体文案。
  - 公开站命名空间：`html`、`common`、`nav`、`marketing`、`auth`、`dashboard`、`settings`、`footer`、`toast`、`errors`
  - 后台命名空间：`common`、`nav`、`auth`、`dashboard`、`settings`、`userMenu`、`commandMenu`、`errors`
- **key 一一对应**：`en.json` 与 `zh.json` 的叶子 key 集合必须完全相等，既不能缺也不能多。
- **叶子键名语义化**：用 `loginSubmit`、`passwordMismatch` 这类能自解释的名字，不要用 `text1`、`label2`。
- **插值用 ICU 语法**：例如 `footer.copyright` 为 `© {year}. All rights reserved.`，组件侧 `t("footer.copyright", { year: 2026 })`；后台 `dashboard.deltaFromLastMonth` 同理。
- **不要留空字符串**：空值会让界面出现"看起来没翻译"的空白，缺文案时应显式补全或暂时复用已有 key。
- **带富文本的句子拆成多段 key**：例如首页 hero 标题需要给某几个词加强调样式时，拆成 `titleLine1` / `titleAccent` / `titleLine2`，由组件负责拼接与套样式，而不是把 HTML 塞进文案。
- **校验方式**：`just check-i18n-keys`（底层是 `node scripts/check-i18n-keys.mjs`）。CI 的 `frontend-build` job 也会执行同一脚本，缺 key 直接拦红。

### 表单校验文案

`zod` schema 里的校验消息也要走 i18n。注意 **schema 不能在模块顶层构建**，否则消息会被固定在首次求值时的语言上：

```tsx
const t = useTranslations("errors");
// 用 useMemo 把 schema 绑定到当前语言的 t 上
const formSchema = useMemo(() => buildFormSchema(t), [t]);
```

## 新增一门语言需要改什么

以新增 `ja` 为例：

1. 公开站：`i18n/constants.ts` 的 `SUPPORTED_LOCALES` 加 `"ja"`；新增 `messages/ja.json`；`i18n/negotiate.ts` 增加 `ja` 分支。
2. 后台：`src/i18n/init.ts` 的 `SUPPORTED_LOCALES` 加 `"ja"`；`resources` 加 `ja` 条目；`normalizeLocale` 增加 `ja` 分支；新增 `src/locales/ja.json`。
3. 两端语言切换器会自动按 `SUPPORTED_LOCALES` 渲染新选项（无需改动）。
4. 跑 `just check-i18n-keys` 确认三份文案 key 对齐。

## 已覆盖页面与后续清单

本次交付覆盖**基础设施 + 公开站全部可达页面 + 后台核心路由**：

- 公开站：根布局 metadata、导航/页脚、首页、`/about`、`/features`、`/pricing`、登录、注册、仪表盘、设置页。
- 后台：登录页、侧栏/顶栏、仪表盘、设置各子页、命令面板、退出登录等对话框。

公开站当前**没有**保留中文硬编码的页面，`app/` 下的中文只出现在代码注释里。后台若后续新增业务路由，按本页建立的模式迁移文案；未迁移页面接入 i18n 后照常渲染、不报错，也不会显示 key 字面量。

若将来新增业务页面而未同步迁移文案，界面会出现"核心页面双语、新页面中文"的**混态**；这是可接受的过渡状态，按本页模式补齐即可。PRD 的 §12 Risks And Follow-Ups 记录了该跟进项。

## 非目标

以下内容**不在**本能力范围内：

- 后端 API 错误消息的 i18n
- URL 路由前缀式 i18n（`/en/...`、`/zh/...`）
- RTL 布局与阿拉伯语等右书语言
- 自动机器翻译文案
- 文档站（mkdocs）本身的多语言
- 核心页面之外的业务页面一次性全量迁移

## 为什么缺 key 检查不在 pre-commit 里

`.pre-commit-config.yaml` 由模板上游维护（见 `scripts/shared/template/sync_template.sh` 的 `_is_upstream_owned()`），派生项目手改会在下次 `just sync-template` 被覆盖。`docs/ai-standards/tooling.md` 的「项目私有 hook 放哪里」明确要求：项目私有的检查逻辑做成独立脚本，**在 CI 或 `justfile` 中调用**，而不是塞进统一的 pre-commit 配置。

因此缺 key 检查落在：

- `scripts/check-i18n-keys.mjs`（唯一实现）
- `just check-i18n-keys`（本地入口）
- CI `frontend-build` job 的 `Check i18n message key alignment` 步骤（强制拦截）
