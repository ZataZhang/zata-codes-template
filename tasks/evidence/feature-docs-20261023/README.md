# Feature Docs 升级与评估证据

## 输入与实验边界

- 权威源：`skills/feature-docs/`。升级前版本保存在 `baseline-skill/`，首轮新版在
  `candidate-skill/`，按首轮失败修正后的版本在 `retest-skill/`。
- 源码基线与任务见 `manifest.json`。源码来自模板仓库真实 HEAD，叠加当时未提交的规范
  入口和导航。`inputs/common/` 保留叠加文件；受控陈旧文档与接口变更见 `inputs/case-*/`。
- 第 1 项任务补认证功能地图；第 2 项任务同步 `/ready` 改名；第 3 项任务修复不存在的
  入口和虚构依赖检查。后两项受控注入，不代表仓库原先存在这些故障。
- 新旧版各用一名独立 Agent，版本之间上下文隔离，同一版本的三项任务连续执行。并非
  六个独立会话；不能据此断言稳定成功率或消除顺序效应。
- 执行者只能改文档及导航，不安装依赖、不启动服务、不改产品代码或测试。
- 原始文档、DELIVERY、差异、改动清单保存在 `outputs/`。完整源码快照在本机临时目录
  `/tmp/feature-docs-evaluation/`，清理后可按 manifest 与 inputs 重建，不能将临时路径作为永久产物。

## 首轮发现与修正

独立评分者以 A/B 标签比较首轮输出（A 为 candidate、B 为 baseline；执行评分时未给版本映射）。
根代理随后要求专项核实测试初始化边界，因此此项检查是带线索核验，不是完全无提示的发现。

首轮新版误将 `tests/test_health.py` 描述为临时 FastAPI/router-only 测试。实际测试导入
`backend.main.create_app`，调用工厂后又注册 router；使用 ASGITransport 或重复 include_router
不能证明未经过生产工厂。同样，经过工厂也不代表真实 DB/Redis 已验证，需要继续看 fixture。

因此首轮不因平均分可能达到 90 就认定目标完成。失败输出完整保留；skill 增补读取测试体、
fixture、工厂及替身、按实际断言描述覆盖的要求，再用不同 URL 与不同陈旧说明复测两项。
复测输入保存在 `retest-inputs/`，未复用首轮输出。评分标准保持不变。

## 实际检查

- Skill frontmatter 校验通过；规范一致性检查通过。
- 首轮执行者因快照缺少 MkDocs 报告构建不可用，未冒称成功；快照无 `.git` 的检查限制亦有披露。
- 根代理使用模板已有 `.venv/bin/mkdocs` 对六份首轮输出分别严格构建，全部成功。
  日志见各输出的 `mkdocs-build.log`。这是补充文档检查，不是执行者跑过的产品测试。
- `source-integrity.json` 核对源代码、测试、脚本和关键配置，未发现超出受控输入的修改。
- 读者检查只读文档、不看源码；原始回答见 `reader-result.md`。源码核对与最终分数另行记录。
- 任务耗时为执行者自报调查区间，部分收尾交错，不是端到端独占时长。实际 token 用量不可用，
  不以文档长度推算 token，也不宣称节省成本。

最终结果见 `results.md`。这些是本轮小样本文档任务表现，不是跨模型、跨仓库的保证。

## 专项补测与范围纠正

独立读者的源码复核还发现仓库范围影响遗漏：指标排除路径、指标测试、OpenAPI 守卫和双语
README。首轮评估的写权限仅涵盖 docs/ 与导航，影响了根目录文档同步的检验；但未报告
源码消费者仍是输出缺口。评分者已在复测报告中保留原暂评分并追加下调依据，没有覆盖失败记录。

最终版增加仓库范围引用搜索及既有页面矛盾核对，用新的 `/service-ready` 变体、明确允许
维护根 README 的任务交给新执行者。该单项非盲、非配对补测单独评分，不替换首轮结果、
不把多轮最佳分拼成“最终三任务总分”。原始输出和差异见 `outputs/final-sync/`。

补充检查的操作记录：最后一项执行者冻结文档后，根代理收集证据时误在快照目录执行
`uv run`，自动创建虚拟环境并安装快照依赖；随后移除了该环境和误生成的证据副本。
该事件发生在执行结束之后，不属于执行者行为、未改动冻结文档、未运行产品测试，也不计入
耗时或质量增益。严格构建使用模板已有 MkDocs 可执行文件，结果另存日志。
