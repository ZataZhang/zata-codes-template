# 网络配图规范

长文默认配图。公众号读者面对纯文字长文的弃读率很高，图片的作用是断节奏、锚定论点、提供信任感（「作者真的查过」）。

## 配多少、配什么

- 一篇 3000～5000 字的文章配 3～6 张，宁可少而准，不要装饰性堆砌。
- 优先配三类图：**新闻现场**（发布会、设备、工厂）、**关键人物**（文中点名的人物）、**核心产品**（文中讨论的硬件/界面截图）。
- 每张图必须和所在段落的论点直接相关。想不出这张图支撑哪句话，就不要放。
- **更新文章时同步补图。** 给旧文追加新章节（如刚发布的产品、新的数据）时，新章节同样需要配图——只加文字不加图是常见遗漏。

## 来源优先级

1. **Wikimedia Commons（首选）**。版权状态清晰（CC 各版本或公有领域），可直接引用，且有 API 可程序化检索。
2. 官方 press kit / 新闻中心素材（注意版权声明，公众号转载一般可接受但需标注来源）。
3. **Google 图片 / 网络搜索（补充渠道）**。时效性强——刚发布的产品、刚发生的事件，Commons 往往没有，Google 上有官方发布图和媒体报道图。使用时注意：优先选官方来源（OpenAI 博客、公司新闻页）的图；正文里标注来源；截图类内容（发布会画面、官网界面）比摄影师作品的风险低。不要因为「Commons 没有」就放弃配图，先走 Google 这条路再找替代方案。
4. 其他来源需逐一确认授权，不确定就不用。

## 用 Commons API 搜图

```bash
curl -s "https://commons.wikimedia.org/w/api.php?action=query&generator=search&gsrsearch=关键词&gsrnamespace=6&gsrlimit=8&prop=imageinfo&iiprop=url|size&iiurlwidth=1200&format=json"
```

- 关键词用英文（Commons 以英文文件名为主），按 `gsrlimit` 返回缩略图 URL 和尺寸。
- 选宽度 ≥1200px、横竖比适合正文的图。人物肖像可用竖图，产品/场景优先横图。
- 下载到文章目录的 `assets/` 文件夹，文件名用有意义的英文小写（如 `asml_euv_containers.jpg`）。
- **下载后必须用 ReadMediaFile 看一眼**，确认内容真的是你以为的那张图——搜索结果标题可能货不对板（比如搜「Ampere」会混进安培的墓地照片）。

## 时效性事件的替代方案

刚发布的产品/事件（几天内）Commons 上通常还没有对应图片。替代方案按优先级：

1. 事件中**关键人物的肖像**（Commons 一般有），图注里写清此人与此事的关系；
2. **上一代产品或同类场景**的图片，图注注明；
3. 都没有就如实说明「暂无合适图片」，不要用无关图片硬凑。

## 原始素材归档

- 所有进入文章的图片素材——下载的网图、用户在对话里发来的截图、自己截的界面图——**先归档到文章图片目录的 `raw/` 子文件夹，再开始任何加工**。临时目录（/tmp、剪贴板缓存、会话目录）和聊天记录都会消失，只留成品不留原图，日后改构图、改图注、重新合成 GIF 就没米下锅。
- **归档前先完成隐私打码**（见下一节）。`raw/` 会随仓库留存的，别把未打码原图留在里面。
- 裁剪、拼合、合成 GIF 都从 `raw/` 原图重做，参数写在处理脚本里（参考 `make_demo_gif_03.py` 的做法），保证同一处理可复现。
- 成品放图片目录顶层供正文引用，`raw/` 只进原图，两者不要互相覆盖。

## 隐私打码

用户发来的截图默认带隐私：手机号、账号名、同事用户名。发出来给你看的这一张没打码，不代表下一张也没有——**每张都全画面扫一遍，不能假设**。

- **扫哪里**：不止左下角。桌面客户端截图的手机号常在角落固定位置（如 2000px 宽的截图约在 (70,1190)–(210,1226)），但也会出现在对话头部的说话人名、表格的「所有者/更新人」列、弹窗文本里。用户经常自己打码了一部分（像素块盖住成员名）却漏掉另一处，两边都要核对。
- **怎么打**：取样标识文字旁的干净背景色再平填，不要硬编码白色——同一批截图有的是 (242,242,242) 渐变区，有的叠了暗色遮罩（弹窗类截图背景整体变暗），必须逐区域取色。标识信息挨着线条（表格分隔线、边框）时，擦除矩形要收到线内测过。
- **改坐标前先读实际尺寸**：会话里消息标注的「original 3420×2146」常是缩放系数，剪贴板缓存里的实际文件往往存的是显示尺寸（2000×1255）。先用 PIL 打印 `im.size`，再按实际尺寸算遮蔽矩形。
- **打完必须验证**：对每处遮蔽区放大 2～3 倍裁剪逐一 Read 确认——数字没了、底色无痕、旁边元素没被擦掉。
- **成品和 raw/ 都不能有漏网**。文章引用的成品图、归档的原图，隐私标准一致。

### 改截图上的标注文字

用户常在截图上画红字标注和箭头，之后又要求改字（如删掉标注末尾两个词）。做法：

1. 先裁剪放大目标区域，确认字形范围和底下有没有表格线、边框穿过——没有才能按颜色定向擦除，有就只能逐段重建线条；
2. 擦除按颜色阈值做多遍：第一遍删主色笔画（如红色 `r-g>18 and r-b>18`），第二遍扫红色抗锯齿残影（放阈值到 `r-g>8`），第三遍把残留的近白像素（`min(rgb)>240`）归纯白；
3. 完成后放大 2～3 倍验证无残影，再进后续拼图流程。

## 图注规范

每张图配一行斜体图注，格式：

```markdown
*▲ 画面内容的一句话说明，带上它与论点的关系。图：拍摄者或机构 / Wikimedia Commons*
```

- 以 `▲` 开头，与正文视觉区分；
- 说明里要有信息增量，不是重复文件名（「NVIDIA H100——2022 年 10 月禁令的头号目标」，而不是「H100 显卡图片」）；
- 末尾必须标注来源和作者/机构。

## 校验：图、图注、文章三者必须一致

下载后用 ReadMediaFile 看图只是第一步，还要对照文章语境做两层校验：

1. **内容校验**：画面真的是你以为的东西吗？（搜索结果可能货不对板。）
2. **语境校验**：图片的拍摄时间、场合与图注、正文叙述是否矛盾？最常见的坑是用旧照片配新事件——照片里的人确实是那个人，但拍摄于几年前，图注却没有标明，读者会以为照片就来自文中所说的事件。**用旧照片时，图注必须写明拍摄年份和场合**（如「摄于 2019 年 TechCrunch Disrupt」），叙述文字（引语、事件描述）与照片时间要分开表述，不能揉成一句。

## 与公众号排版的关系

- 图片在公众号后台不会随 HTML 粘贴带过去，交付时要列出需手动重传的图片清单；
- 图注在构建出的公众号 HTML 中会被渲染为小字居中样式，无需额外处理。
