# X 推文与配图帖

用户要求写 X 文案、推文或配图帖时读取本指南。默认先写一条能独立读懂的短帖；只有用户要求 Thread，或一条短帖确实讲不清时，才拆成多条。

## 单条推文的表达顺序

围绕一个读者、一个核心信息和一个目的来写。常见结构是：

1. **从具体问题或场景开头**：让目标读者知道为什么值得看。优先写读者正在遇到的摩擦或一个具体变化，少用「我做了个新功能」这类没有信息量的开场，也不编造数据、经历或用户反应。
2. **说明改了什么**：用一句话点出项目、功能和变化。可以用第一人称，但只有在素材能确认作者确实参与时才写「我做了」。
3. **解释读者能怎么用**：挑最能说明价值的动作或因果链来写。工程功能可以呈现为「先看到什么 → 接下来能做什么 → 得到什么结果」。避免把文件名、实现细节和功能清单全塞进一条推文。
4. **收在一句结论或行动提示**：例如一句简短的使用原则。它应从前文自然推出，不另起一个夸张口号。
5. **链接按需放在末行**：用户指定的仓库、文档、Skill 或产品页面优先；只放一个最相关的主链接。不要擅自加其他仓库链接或多个 CTA。没有必要时可以不放链接。

先写清楚信息，再调整口语感和节奏。中文短帖通常用两到三个自然段，留出阅读停顿；不为了「像社交媒体」而堆 emoji、标签、反问或网络梗。写 Thread 时，每条只推进一个信息点，首条独立交代主题，末条收束观点或放链接，不为了拉长内容强行拆帖。

## 配图与截图

- 先确定每张图要证明什么，再决定是否附上。图文共同讲一个主题，正文交代读者该看什么，图片提供界面或实现证据，不要逐张复述画面。
- 多张图按读者理解顺序排列；工程功能可从整体界面开始，再展示关键交互、对应代码或复杂链路。按实际素材取舍，不固定图片数量，也不为了凑数加装饰图。
- 检查手机尺寸下关键文字是否可读，裁掉无关浏览器边框和空白，但保留理解界面所需的上下文。
- 发布前检查截图中的姓名、邮箱、令牌、客户资料、私有仓库信息、分支和提交标识。需要时做脱敏；若图中内容被替换、合成或只用于演示，要在文案或图像说明中明确标为示例，不能让示意图冒充实际运行结果。
- 图片中的细节不应支撑正文没有写过的结论。可用平台支持的替代文本说明图片内容，不能只靠图片传达关键信息。

## 完稿核对

- 读者能否在开头两句内说出这条推文的主题？整条是否只有一个主信息？
- 功能描述、第一人称、效果和配图是否都能由用户素材、代码或真实截图支持？
- 图片顺序是否形成清楚的理解路径？隐私信息是否已处理？
- 链接是否指向用户要分享的目标，且没有带入不相关的仓库？
- 用户要的是可复制文案时，交付正文和建议配图顺序，不替用户发布。用户明确要求在平台里编辑或发布时，再按当前授权范围操作；平台字符计数、媒体规则或界面已变化时，以当前平台显示为准，不硬编码旧限制。
