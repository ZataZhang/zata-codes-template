# 项目周报与阶段进度汇报

用于内部项目的周期性工作总结、研发周报和阶段进度报告。目标是让读者看清本期成果、这些成果改变了什么、交付证据处于什么状态，以及接下来需要完成或协调的事项。它不是按日期罗列工单的流水账，也不是把完整代码变更记录贴进正文；提交记录（commit hash、PR 清单）是核验材料，不是报告内容。

## 先确定时间范围和对照基线

- 标明项目、报告周期和检查日期。使用“第 N 周”时，遵守团队的周次口径，并同时写明起止日期，避免不同周历产生歧义。
- 有上一期报告时，把它当作基线：只更新发生变化的能力、阶段状态和待办；上一期仍然有效的背景用链接承接，不整篇重写。
- 区分事实来源：仓库状态、PR/commit、自动化验证、部署记录、真实运行或人工验收分别能证明什么。用户提供的记录与代码证据不一致时，指出差异并保留待确认项。
- 目标读者和时间范围可从上下文确定时直接推进；缺失信息不影响成稿时标注范围或证据缺口，不补造日期、指标和项目状态。

## 组织本期进展

开头先给一两句本期判断，让读者知道最重要的成果和当前状态。然后围绕成果组织正文，而非逐日或逐 PR 排列。每项重点变化按需要说明：

1. 之前遇到的实际问题或限制。
2. 本期做了什么，员工、管理员或业务流程现在能做什么。
3. 一种具体使用场景，以及适用边界。
4. 实现或交付证据，以及尚未完成的验证。

结构性内容优先用图，不写成段落：链路、时序、票据/令牌交换、跨系统调用、状态总览这类一图讲清的部分都画成示意图，正文只留结论句、状态和下一步。示意图须自标注「示意图」并与真实截图分开；录屏证据用抽帧拼图呈现，图注附完整录屏链接。

长一点的阶段报告可以增加时间线，帮助读者看清阶段重心如何变化；周报只有一两项成果时，保持短篇，不为套结构扩写。能力全景可以作为第一期基线；后续报告重点写增量、状态变化和上次遗留问题的处理结果。

## 在报告里呈现代码

技术代码可以作为进度证据和解释材料，不需要为了管理层读者而全部删掉，也不应把大段代码直接丢给读者。

- 只有代码本身能说明关键行为、边界或实现决策时，才选一小段代码、配置或前后差异。优先引用真实仓库路径及对应 PR/commit；没有可核对的源码时，使用用户提供的 PR 描述并清楚标成记录来源，不自行补写代码。
- 摘录后紧接一句说明它改变了什么，以及对交付、使用者或维护有什么影响。术语首次出现时先解释作用，再保留可搜索的技术名词。
- 代码片段只证明片段所示内容。它不能单独证明构建通过、已经部署或业务验收完成；这些状态要引用各自的验证证据。
- 大型 diff、完整日志、完整测试输出放到 PR、commit 或附件链接里。正文保留能支撑判断的几行和验证结果。
- 不需要代码时，用准确的 PR/commit 链接和简短改动说明即可，不要为满足“技术报告”而硬加代码块。
- 提交记录按读者分层：面向管理者或业务方的汇报不写 commit hash，也不设 PR/commit 清单——它们对判断进度没有帮助。记录留在交付说明或团队工作流里核验；正文确需追溯时，链接到 PRD、帮助文档、演示录屏这类读者看得懂的交付物。

## 状态、风险和下一步

对重要事项分别记录当前状态和证据。按项目实际口径，可区分“已实现”“已合入”“构建/测试通过”“已部署”“人工验收完成”“暂缓”“未开工”；它们不是可以互换的同义词。路线图、代码和验收记录口径不一致时，明确写出差异，不替项目裁定。

说明尚未完成的事项时，讲清它影响什么、下一步如何验证，已知时再补负责人、时间点或依赖。需要管理者协调或决策时，写明要决定的具体事项、选项或影响；材料没有提供请求时，不虚构“需领导支持”。没有可靠口径和分母时不写整体完成百分比。

长篇报告可使用实际产品截图、设计原型或流程图解释变化，图注区分其证据等级并标明日期、版本或验证状态。原型不能证明功能已经完成，流程图不能代替端到端验收。

## 可调整的篇章顺序

- 标题：项目名、报告周期，以及最值得关注的结果。
- 本期判断：成果、当前阶段或关键结论。
- 重要进展：按结果或工作流分组，附必要的代码、界面或验证证据。
- 状态与未闭环：完成、待验证、暂缓和风险分开呈现。
- 下一步：下个检查点、依赖和明确的协调/决策请求。
- 来源：默认不设此段；确需追溯时给 PRD、文档、演示等读者看得懂的直达链接，不列 commit hash、PR/commit 清单。

这是一组可删减的内容，不要求每份周报都设置同样的章节。需要工作汇报口径时，读取[工作汇报风格](styles/work-reporting.md)，并按汇报对象、目的调整细节层级与正文长度。

## 交付前检查

- 周期和基线明确，读者能看出这次相较于之前发生了什么变化。
- 核心成果用使用影响或交付结果表达，技术细节有证据且能追溯。
- 代码合入、构建/测试、部署和人工验收没有混写。
- 未完成事项、风险、下一步和协作请求来自真实材料；缺项明确标注。
- 没有堆砌日报、PR/commit 清单、无口径的百分比或无法核实的收益数字。
