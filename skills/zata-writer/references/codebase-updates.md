# 代码库更新与追踪写作

目标：先让读者理解项目当前支持哪些主要功能、能完成什么任务，再判断变化是否值得改变现有做法，并在后续追踪中验证此前判断。围绕使用影响组织正文，避免逐条翻译 changelog。

## 选择主线

| 类型 | 主线 | 所需证据 |
|---|---|---|
| 当前功能全景 | 现在能做什么，各项能力怎么配合，边界在哪里 | 目标版本的文档目录、功能页、示例及必要的源码核查 |
| 版本更新解读 | 哪些变化值得关注，升级有什么代价 | 发布范围、行为差异、兼容性与迁移说明 |
| 功能追踪 | 原来解决不了什么，现在做到哪一步 | 不同版本的能力和限制，具体使用场景 |
| 项目方向观察 | 连续变化指向什么方向 | 多个版本的共同趋势、反例；区分官方计划和作者推断 |
| 实践跟进 | 实际解决了什么问题，还剩什么限制 | 真实操作、版本、环境、输入与结果 |

一篇确定一个主要问题，其他类型只在支撑主线时穿插。只有一项值得展开的变化时，直接写短篇，不凑多项或完整长文。

## 确定范围与证据

- 写清检查日期、具体仓库或包、起止版本或日期。生态内不同组件分别确认版本，不把整个生态视作同一发布单元；公开和内部代码库均适用。
- 首次追踪没有历史基线时，写当前能力和已知限制，不虚构前后差异。用户未给范围时，先读取目标项目已有追踪记录；仍缺失则根据文章目的选择范围并说明。
- 区分已发布、预发布、已合并未交付、提案或开放 PR。合并记录不能单独证明功能已向目标读者提供。
- release/tag 或起止 commit 确认变化范围，目标版本的项目文档确认用法，源码和测试核查关键行为，issue/PR 帮助理解背景。网站最新文档可能领先于目标版本；优先使用对应版本的资料或固定 tag/commit。内部代码库没有公开发布记录时，使用可访问的变更记录并说明证据边界。
- 每个关键事实链接到直接支持它的一手来源。涉及行为或兼容性的判断，资料不足时查代码或做最小验证；不能确认就标明缺口，不推断为已支持。
- 第一人称亲测需要真实执行证据。资料分析写清依据；跑通过示例只能证明该场景，不外推为生产稳定性或普遍性能提升。

## 当前功能全景：先建立能力地图

用户问“现在支持哪些功能”“全面介绍这个项目”时，以当前功能全景为主线；首次系统追踪或维护项目总览时，也要建立这一层。解释深度应比项目首页清楚，覆盖主要功能领域和重要边界；具体参数、完整 API、安装操作与详细教程留给项目文档，并给出入口链接。

- 从项目文档目录、功能页和示例整理主要能力，README 仅作为定位入口；不能只用最近的 release 拼出功能清单。与目标版本对齐，无法确认的能力标明缺口，不宣称穷尽全部功能。
- 按使用者的任务分组，保留重要组件名称作索引。避免只列术语、包名或营销卖点。每类说清：解决什么问题、支持哪些具体动作、一个输入到结果的场景、必要条件与限制。
- 区分项目本体、可选官方组件、外部集成和商业服务。接入外部系统与内置实现含义不同；标明依赖、付费条件或预览状态，不能把整个生态的能力都归给主仓库。
- 总表帮助定位，逐类正文解释能力，最后用一个具体任务串起模块关系。只有在关系复杂时画图，不为凑图加入装饰。
- 当前支持的能力和本次新增能力分开说明；没有变化的核心功能也属于全景。通常选两到四项变化展开的数量建议，不限制全景覆盖的功能类别。
- 专题更新短篇可用一段定位并链接已维护的功能总览；用户明确要求当前功能全景时，不能用旧文链接替代本次版本核验与必要的功能解释。

## 筛选值得写的变化

优先选择能直接支持读者决策的内容：过去需要绕路实现的能力、现有代码的行为或兼容性变化、成本或性能或可靠性的变化，以及连续版本中有证据的方向变化。

逐项问：不告诉读者，他会错过什么，或踩到什么坑？无法说明影响的改动省略或放进简表。一般展开两到四项即可，数量服从实际价值。没有实质变化时，允许交付简短跟进或建议本轮不单独成文，不制造趋势或重要性。

## 展开每项变化

按需要采用这条因果链：原来的问题 → 本次改动 → 一个具体例子 → 适用边界 → 读者行动。

- 前后对照落到同一个场景。用代码、调用流程或结果说明过去怎么做、现在怎么做；涉及多个条件变化时不要把收益全部归因于本次更新。
- 新增能力说明前置条件、默认行为、失败条件和外部依赖；性能或成本数字交代对照版本、环境、工作负载和数据来源。
- 代码标明适用版本。迁移示例保持输入和目标一致，突出必须调整的部分；未运行时不得称为已验证可运行。
- 发布事实、机制解释和作者判断分清。方向判断需要多个变化共同支持，并检查反例，单个功能不足以证明战略转向。
- 建议按人群和条件给出：哪些新项目可以采用、哪些存量项目需要先迁移、哪些用户暂时无需行动。不笼统宣布“所有人都值得升级”。

例如，假设某个框架新增任务恢复能力，应追问：之前中断后怎么处理，现在从哪里恢复，哪些状态被保存，外部操作是否会重复，接入要改什么。这是解释功能价值的提问示例，不是对任何具体项目能力的断言。

## 接续历史追踪

阅读项目中的前文与追踪记录：上次的限制是否解决，计划是否落地，推荐方式是否弃用，旧判断是否需要修正。正文只引用读者需要的历史，避免每篇重复完整项目介绍；首篇没有前文时省略这一部分。

新建文章还是更新旧文，遵循目标项目策略和用户要求。更新旧文时保留适用时间或版本边界；纠正旧判断要说明原结论及修正依据，避免静默覆盖让历史失去意义。检查日期、已覆盖版本、待研究事项等持久状态留在目标项目，沿用现有格式；没有状态文件且用户只要求写文章时，不额外搭建监测系统或定时任务。

### 项目进度报告与阶段跟进

用户要续写「今天的进度」「最近进展」或阶段报告时，先确认目标读者和时间范围。若用户给出上一版报告，把它同时作为事实基线和呈现参照：检查它怎样解释术语、组织章节、使用真实截图或示意图、标注证据状态；延续仍适用的读者体验与视觉层级，再更新内容。不要把一份面向业务读者的图文报告自动改写成只列 PR、PRD 和状态标签的研发清单。

面向非技术或混合读者时，优先讲清三件事：员工现在能做什么、管理员能看到或控制什么、还有什么没有完成。每项重要变化按「原来卡在哪里 → 现在能做什么 → 一个具体使用场景 → 适用边界」解释；专业词首次出现时先用日常语言说明，再保留必要的英文名称供查找。PR 编号、测试细节和验收文件放在贴近事实的出处或文末来源区，不让它们替代功能解释。

把「代码已合入」「已经发布」「真实入口已验证」「人工验收完成」「暂缓」和「尚未开工」分开写。阶段间不使用缺少依据的统一百分比；如路线图和验收记录口径不一致，明确指出并保留待对齐状态，不替项目悄悄裁定。

长篇产品进度报告要用具体产品画面或机制图支撑主要变化。能找到且与当前事实相符的真实运行截图时优先使用；没有真实画面时，可用设计原型或流程示意解释，但图注必须分别标明「真实界面」「设计原型」或「流程示意」。注明截图对应的日期、版本或验证层级；原型不证明当前产品状态，流程图不证明整条链路已经通过验收。避免只用抽象架构图或术语卡片代替能让读者看懂的产品画面。

## 可选文章骨架

需要直接起稿时，复制 [Markdown 文章模板](../assets/templates/codebase-tracking.md)，替换占位符并删除不适用章节；frontmatter 和封面按目标项目补齐。

按主线删减或重排，不把核验日志搬进正文：

1. 开头：最值得关注的变化，以及谁需要看。
2. 追踪范围：检查日期、组件和版本范围，可并入开头。
3. 当前功能全景：按任务分组的能力总表、具体功能说明、协作流程与边界。
4. 关键变化：逐项解释问题、改动、例子、边界和影响。
5. 现有项目怎么处理：兼容性、迁移成本及行动条件。
6. 上次问题的进展：有历史记录时回访和修正判断。
7. 后续观察：列有依据、能验证的问题；无需另写重复总结。

标题突出变化或使用影响，只有版本号会缺少读者价值。短篇用必要的代码对照、表格或机制图即可，不凑正文图片；长篇遵守主入口的配图规则，封面遵守目标项目约定。

## 交付前检查

结合通用编辑自检，再确认：全景覆盖主要能力且有具体场景；本体与生态边界清楚；当前支持与本次新增分清；范围可复查；发布状态没有混淆；证据对应目标版本；前后对照条件一致；建议有适用人群；没有伪装亲测；历史判断已核对或说明无基线。无法核验的事实和未运行的示例，在交付说明中披露。
