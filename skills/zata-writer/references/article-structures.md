# 文章结构模板

根据任务选择最接近的一种结构。模板是默认骨架，不是必须逐项照抄的表格。

## 技术原理与工程实践

适用于架构、框架、源码和工程问题。

1. 具体问题与结论预告
2. 概念和边界
3. 底层原理或调用链
4. 当前实现及证据
5. 可选方案对比
6. 推荐落地方式
7. 风险、限制和验证方法
8. 总结与行动清单

读者应该能回答三个问题，为什么、怎么做、什么时候不该这样做。

## 论文与研究解读

适用于论文精读、技术报告和基准评测解读。读者通常是想判断「这个方法我能不能用、结论该不该信」的工程师，不是审稿人。论文的章节顺序服务审稿，文章的顺序服务读者的决定，不要照着论文目录复述。

1. 用论文里的一个具体案例或数字开场，并在第 3 步兑现它
2. 一句话说清论文声称什么、跟谁比
3. 用开场案例把机制走一遍；每个术语第一次出现时给一句直觉解释（logits、advantage、KL 这类词，读者未必熟）
4. 证据撑不撑得住声称：只摆公平对照（同基座、同预算、同数据），每个数字标明对照组；不公平的对比点明差在哪，并用同一把尺子检查全文所有对比
5. 代码和仓库里看到的：论文没交代的实现细节、与论文不一致的地方、复现条件（模型快照、默认参数、依赖的服务）
6. 我能不能用：前置条件、成本、适用和不适用的场景、上线前要补的防护
7. 仍然没有答案的问题：只列查过论文、代码、README、issue 之后仍答不了的

写法要点：

- 结果表只搬支撑论点的几行几列，完整表给链接。
- 定理只讲它保证了什么、不保证什么、离实验有多远；假设清单除非是论点所需，不逐条搬运。
- 作者的解释站得住就直接用，不必逐条写「我认同」；站不住或有补充时才写自己的判断和理由。

## 产品或工具对比

先定义共同维度，再介绍产品，避免每个产品各说各话。

建议维度包括定位、核心能力、隔离或可靠性边界、生态集成、状态与持久化、部署方式、成本模型、成熟度和适用场景。

正文可以逐项展开，但结尾必须给一张总表，以及按场景给出的选择建议。不要宣布一个脱离场景的「全局冠军」。

## 方法论文章

1. 作者为什么形成这套方法
2. 方法解决什么问题，不解决什么问题
3. 3～7 个核心原则，每个原则包含原因、例子、动作和常见失败
4. 一套可直接执行的流程或清单
5. 学习成本和适用前提
6. 总结

不要只展示理想结果。明确写出初期低效、工具限制和需要人工判断的环节。

## 产品体验

只有确有使用证据时采用第一人称体验结构。

1. 使用动机和测试环境
2. 最关键的 2～4 个场景
3. 每个场景的输入、过程、结果和判断
4. 与既有方案对比
5. 优点、缺点和适用用户
6. 最终判断

没有真实体验时改写成「产品分析」，不要模拟使用过程。

## 现象解读与行业观察

1. 一个具体事实或变化
2. 表面解释
3. 更深层的结构性原因
4. 支持与反对证据
5. 对开发者、团队或普通用户的影响
6. 作者判断及其不确定性

文化、历史或哲学类比只有在确实帮助理解时使用，不为了升华而升华。

## 开源项目追踪

当前功能全景、版本更新解读、功能演进、项目方向观察和实践跟进，按 [open-source-updates.md](open-source-updates.md) 选择主线和结构，需要直接起稿时使用 [Markdown 文章模板](../assets/templates/open-source-tracking.md)。短篇可以只展开一项有意义的变化，不套用完整长文骨架。
