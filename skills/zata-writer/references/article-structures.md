# 文章结构模板

根据任务选择最接近的一种结构。模板是默认骨架，不是必须逐项照抄的表格。

## 技术原理与工程实践

适用于架构、框架、源码和工程问题。

1. 具体问题与结论预告
2. 概念和边界
3. 底层原理或调用链
4. 当前实现及证据
5. 可选方案对比
6. 推荐落地方式
7. 风险、限制和验证方法
8. 总结与行动清单

读者应该能回答三个问题，为什么、怎么做、什么时候不该这样做。

## 产品或工具对比

先定义共同维度，再介绍产品，避免每个产品各说各话。

建议维度包括定位、核心能力、隔离或可靠性边界、生态集成、状态与持久化、部署方式、成本模型、成熟度和适用场景。

正文可以逐项展开，但结尾必须给一张总表，以及按场景给出的选择建议。不要宣布一个脱离场景的「全局冠军」。

## 方法论文章

1. 作者为什么形成这套方法
2. 方法解决什么问题，不解决什么问题
3. 3～7 个核心原则，每个原则包含原因、例子、动作和常见失败
4. 一套可直接执行的流程或清单
5. 学习成本和适用前提
6. 总结

不要只展示理想结果。明确写出初期低效、工具限制和需要人工判断的环节。

## 产品体验

只有确有使用证据时采用第一人称体验结构。

1. 使用动机和测试环境
2. 最关键的 2～4 个场景
3. 每个场景的输入、过程、结果和判断
4. 与既有方案对比
5. 优点、缺点和适用用户
6. 最终判断

没有真实体验时改写成「产品分析」，不要模拟使用过程。

## 现象解读与行业观察

1. 一个具体事实或变化
2. 表面解释
3. 更深层的结构性原因
4. 支持与反对证据
5. 对开发者、团队或普通用户的影响
6. 作者判断及其不确定性

文化、历史或哲学类比只有在确实帮助理解时使用，不为了升华而升华。
