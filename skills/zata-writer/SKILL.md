# Zata Writer

以 Zata 的方式写中文长文。目标不是模仿文学腔，而是让读者快速看懂一件复杂的事，并相信作者真的理解、验证和思考过它。

## 写作取向

- 清晰优先。默认使用二级、三级标题，把问题、证据、比较、结论分开。
- 观点优先。开头尽快说明文章解决什么问题，以及作者当前的核心判断。
- 证据优先。技术事实、版本、产品能力和数据必须可核验；时效性内容先查官方来源。**榜单、跑分、排名类数据必须核到一手来源（官方发布页、官方模型卡、评测机构官网），聚合站和 SEO 博客只能当线索，不能当依据**；聚合站之间的数字互相矛盾时，以一手来源为准并在图注/正文标注「自报」「待独立复测」等证据等级。
- 真实优先。可以写第一人称，但只使用用户提供或当前任务中真实发生的经历，不编造体验、对话、数据和情绪。
- 有人味，但克制。允许自然口语、自嘲和明确好恶，不靠密集网络梗、夸张标点或故意断句制造风格。
- 可执行。方法论和技术文章要给出读者下一步能采取的动作，并坦诚说明成本、限制和失败条件。

## 默认工作流

1. 吃透用户提供的素材，确认文章受众、目的和核心问题。上下文足够时直接推进，不重复询问。
2. 判断哪些信息可能变化或需要精确引用。需要调研时优先使用官方文档、论文、源码和一手公告。
3. 先形成一句核心判断，再设计结构。不要边写边堆资料。
4. 根据文章类型选择结构。需要详细模板时读取 [references/article-structures.md](references/article-structures.md)。
5. **配图是默认动作，不是可选项。** 长文至少配 3 张与论点直接相关的图片（新闻事件、关键人物、核心产品），写入 `assets/` 并逐张验证。具体来源、检索方法和图注规范见 [references/web-images.md](references/web-images.md)。
6. 完成初稿后按 [references/editorial-checklist.md](references/editorial-checklist.md) 自检并修订。
7. 用户指定目标仓库或发布平台时，先读取并遵守该目标的 `AGENTS.md`、front matter、资源和验证约定。写作风格服从本 Skill，文件组织服从目标项目。

## 默认文章结构

除非用户给出其他结构，使用下面的骨架，并按内容删减不需要的部分。

```markdown
# 标题

开头用 2～4 段交代具体问题、背景和核心判断。

## 一、问题是什么

定义边界，解释为什么值得讨论。

## 二、关键原理或背景

只补充理解后文真正需要的知识。

## 三、方案、案例或产品对比

按统一维度逐项分析，必要时使用表格。

## 四、怎么选择或怎么实施

给出适用条件、步骤、成本和风险。

## 五、我的判断

明确结论，并说明结论成立的前提。

## 总结

回扣问题，提炼 3～5 个结论或行动项。
```

## 段落和列表规则

- 每段集中表达一个意思，通常 2～5 句。避免连续十几个单句形成碎片流。
- 一个章节超过约 600～800 字时，考虑增加三级标题。
- 三项以上并列信息优先使用列表、表格或编号，不强行揉成散文。
- 比较多个产品时先定义共同维度，再逐项展开，最后给出总表和选型建议。
- 代码、命令、配置和数据用代码块或表格承载，不在正文里绕着描述。
- 标题必须提供导航价值。避免只有情绪、没有信息的标题，也避免每两段就插一个标题。

## 语言边界

- 使用自然、直接的中文，保留必要的英文技术名词。
- 可以使用「我认为」「我的判断是」「这里容易踩坑」，但不要每段重复表态。
- 不使用空洞开场，如「随着时代快速发展」或「在当今社会」。
- 少用「首先、其次、最后」「综上所述」「值得注意的是」等报告套话，改用有信息的标题和具体过渡。
- 不为了显得像真人而故意加入大量「。。。」「？？？」、粗口、口癖或句式断裂。
- 不把绝对化语气当判断力。结论要同时写出适用条件、反例或不确定性。

## 吸引力：让文章被读完

「清晰」不等于「平淡」。研究报告式的写法（抽象开场 + 均匀分节 + 平铺直叙）是初稿最容易滑入的状态，要主动对抗：

- **开头用场景，不用概念。** 从一个具体的时刻、事件或画面切入（「2022 年 10 月 7 日，周五，华盛顿。美国商务部扔出了一份一百多页的文件……」），而不是从「某某问题值得讨论」开始。场景里要有具体时间、地点、动作。
- **正文要有叙事细节。** 抽象论点靠具体故事落地：一张没被交付的订单、一次扫货式囤积、一场先禁后放的游说。细节必须真实可核验，不能为了生动而编造。
- **标题写判断，不写标签。** 「先拆一个误读：光刻机从来不是『养肥再杀』」比「光刻机制裁的背景」有力得多。每个标题本身就该是一个值得读的句子。
- **控制节奏。** 长短段落交替；关键判断可以单独成段；连续三段以上同样长度的段落要拆开或合并。
- **结尾落到一句话判断。** 总结之外，给读者一句能记住、能转述的话（「先手是对的，但先手不包赢」）。
- **更新文章时同步更新吸引力。** 追加新内容（如最新的产品发布、数据）时，不能只堆事实段落，要顺手补图、检查新旧段落的开头和标题是否还成立。

## 交付要求

- 直接交付完整文章或写入用户指定位置，不只给提纲，除非用户只要求提纲。
- 正文中的引用紧贴对应事实，优先链接到原始来源。
- 不虚构作者经历。缺少第一手材料时，用研究和推理支撑文章，不伪装成亲测。
- 如无法完成构建、渲染或事实核验，明确披露未验证项。
- 不附带冗长的写作过程说明；交付时简要说明文件位置、覆盖范围和验证结果。

## 可选：发布到公众号

用户要求把成稿发布或排版到公众号时，读取 [references/gongzhong-publish.md](references/gongzhong-publish.md) 并按其流程执行：用 `assets/gzh_build/` 中的构建脚本和主题样式，把 Markdown 转成可直接粘贴进公众号后台的 HTML，挑选金句做荧光高亮，用无头 Chrome 截图验证排版，并向用户说明图片需手动重传、正文外链不可点等平台限制。

## 维护：Skill 本体的修改与部署

本 Skill 的源头是模板仓库 `~/code/zata_code_template/skills/zata-writer`（下称仓库副本）；各 AI 工具加载的 `~/.xxx/skills/zata-writer` 等目录（下称安装副本）只是部署产物，没有版本控制。

**修改一律落在仓库副本，不要直接改安装副本。** 直接改安装副本会让两处分叉，之后任何方向的同步都可能把改动静默覆盖：2026-09-09 的两次事故（过期的安装副本把仓库刚补的 121 行实测结论抹掉；仓库里的旧措辞被抢在复核前提交进历史）都源于编辑面装反。

对 Skill 本体做任何修改（SKILL.md、references/、assets/ 的新增或改动）后，完成两件事：

1. **更新 description 里的时间戳**：front matter 的 `description` 以 `[Updated YYYY-MM-DD]` 开头，每次修改都把它改成当天日期（与 code-reviewer、idea-inbox 等 Skill 的约定一致），方便在 Skill 列表里一眼看出新旧。
2. **部署到各安装副本**。在模板仓库根目录执行：

   ```bash
   ./scripts/sync_template.sh --skill zata-writer
   ```

   非交互、只更新已安装该 Skill 的本机目录（~/.qoder-cn、~/.claude、~/.codex、~/.cc-switch、~/.pi、~/.kimi-code），不会在任何工具里凭空创建安装目录；首次装到新工具用交互式的 `just sync-local-skills`（fzf 逐项预览 diff）。提交前想先在安装副本上验证改动，可以提前部署，但仓库侧的提交始终由用户复核后决定。

**不要把安装副本同步回仓库。** `assets/sync_upstream.sh` 仅作急救保留：只有安装副本被直接改过、需要把改动抢救回仓库时才用它。它把无版本控制的副本单向覆盖进 Git 仓库——脚本守卫能挡住文件删除，挡不住仓库已提交内容被旧副本盖回，用完必须人工逐行复核 diff 再决定提交。

交付时向用户确认时间戳已更新、部署已执行。
