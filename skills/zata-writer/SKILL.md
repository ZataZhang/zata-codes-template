# Zata Writer

以 Zata 的方式写中文长文。目标不是模仿文学腔，而是让读者快速看懂一件复杂的事，并相信作者真的理解、验证和思考过它。

## 写作取向

- 清晰优先。默认使用二级、三级标题，把问题、证据、比较、结论分开。
- 观点优先。开头尽快说明文章解决什么问题，以及作者当前的核心判断。
- 证据优先。技术事实、版本、产品能力和数据必须可核验；时效性内容先查官方来源。
- 真实优先。可以写第一人称，但只使用用户提供或当前任务中真实发生的经历，不编造体验、对话、数据和情绪。
- 有人味，但克制。允许自然口语、自嘲和明确好恶，不靠密集网络梗、夸张标点或故意断句制造风格。
- 可执行。方法论和技术文章要给出读者下一步能采取的动作，并坦诚说明成本、限制和失败条件。

## 默认工作流

1. 吃透用户提供的素材，确认文章受众、目的和核心问题。上下文足够时直接推进，不重复询问。
2. 判断哪些信息可能变化或需要精确引用。需要调研时优先使用官方文档、论文、源码和一手公告。
3. 先形成一句核心判断，再设计结构。不要边写边堆资料。
4. 根据文章类型选择结构。需要详细模板时读取 [references/article-structures.md](references/article-structures.md)。
5. 完成初稿后按 [references/editorial-checklist.md](references/editorial-checklist.md) 自检并修订。
6. 用户指定目标仓库或发布平台时，先读取并遵守该目标的 `AGENTS.md`、front matter、资源和验证约定。写作风格服从本 Skill，文件组织服从目标项目。

## 默认文章结构

除非用户给出其他结构，使用下面的骨架，并按内容删减不需要的部分。

```markdown
# 标题

开头用 2～4 段交代具体问题、背景和核心判断。

## 一、问题是什么

定义边界，解释为什么值得讨论。

## 二、关键原理或背景

只补充理解后文真正需要的知识。

## 三、方案、案例或产品对比

按统一维度逐项分析，必要时使用表格。

## 四、怎么选择或怎么实施

给出适用条件、步骤、成本和风险。

## 五、我的判断

明确结论，并说明结论成立的前提。

## 总结

回扣问题，提炼 3～5 个结论或行动项。
```

## 段落和列表规则

- 每段集中表达一个意思，通常 2～5 句。避免连续十几个单句形成碎片流。
- 一个章节超过约 600～800 字时，考虑增加三级标题。
- 三项以上并列信息优先使用列表、表格或编号，不强行揉成散文。
- 比较多个产品时先定义共同维度，再逐项展开，最后给出总表和选型建议。
- 代码、命令、配置和数据用代码块或表格承载，不在正文里绕着描述。
- 标题必须提供导航价值。避免只有情绪、没有信息的标题，也避免每两段就插一个标题。

## 语言边界

- 使用自然、直接的中文，保留必要的英文技术名词。
- 可以使用「我认为」「我的判断是」「这里容易踩坑」，但不要每段重复表态。
- 不使用空洞开场，如「随着时代快速发展」或「在当今社会」。
- 少用「首先、其次、最后」「综上所述」「值得注意的是」等报告套话，改用有信息的标题和具体过渡。
- 不为了显得像真人而故意加入大量「。。。」「？？？」、粗口、口癖或句式断裂。
- 不把绝对化语气当判断力。结论要同时写出适用条件、反例或不确定性。

## 交付要求

- 直接交付完整文章或写入用户指定位置，不只给提纲，除非用户只要求提纲。
- 正文中的引用紧贴对应事实，优先链接到原始来源。
- 不虚构作者经历。缺少第一手材料时，用研究和推理支撑文章，不伪装成亲测。
- 如无法完成构建、渲染或事实核验，明确披露未验证项。
- 不附带冗长的写作过程说明；交付时简要说明文件位置、覆盖范围和验证结果。
