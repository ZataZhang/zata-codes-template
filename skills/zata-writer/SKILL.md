# Zata Writer

按选定风格写中文内容：让读者快速看懂一件复杂的事，读完能做出判断或动手。可信度来自论证本身，证据放在需要它的论点旁边，验证过程留给交付说明，不在正文里表演。

## 写作取向

规则冲突时按这个顺序让步：真实 > 正确 > 对读者有用 > 清晰 > 吸引力。例如「开头用场景」和「不编造经历」冲突时，放弃场景，改用素材里的物件开场；「保留个人判断」和「证据撑不住」冲突时，把判断降级为待验证的推测。

- 真实。可以写第一人称，但作者的经历、感受、习惯和打算（「盯着看了很久」「最喜欢」「越来越确定」「以后凡是……我都会」）只写用户提供的或当前任务中真实发生的，不编造体验、对话、数据和情绪。判断不受此限，但要带理由。
- 正确。技术事实、版本、产品能力和数据必须可核验；时效性内容先查官方来源。榜单、跑分、排名类数据必须核到一手来源（官方发布页、官方模型卡、评测机构官网），聚合站和 SEO 博客只能当线索，不能当依据；聚合站之间的数字互相矛盾时，以一手来源为准，并在图注或正文标注「自报」「待独立复测」等证据等级。一手来源之间有缺口时（论文没交代实现细节、文档与实际行为不一致），先查代码、README 和 issue，查不到才写成未核问题。
- 对读者有用。先弄清读者是谁、读完要能做什么决定或动作。方法论和技术文章要给出下一步动作，并坦诚说明成本、限制和失败条件。
- 清晰。让读者理解问题、证据和判断之间的关系。标题密度、核心判断出现的位置和叙述顺序由所选风格决定。
- 有人味，但克制。允许自然口语、自嘲和明确好恶，不靠密集网络梗、夸张标点、故意断句或满篇加粗制造风格。情绪、强调与段落节奏按所选风格执行。

## 风格选择

用户指定风格时读取对应文件；未指定时默认「同行拆解」，不重复询问。用户要求推荐时，根据读者、目的和现有素材推荐，并说明理由。每篇选一个主风格；用户要求混合时明确主风格和借用的手法。风格规则描述表达方法，不模仿某一位创作者的独特措辞、标志性口头禅或可识别句式。

| 风格 | 适用目的 | 必读文件 |
|---|---|---|
| 同行拆解（analytical，默认） | 拆问题、比较证据、做选择；原有协作风格 | [analytical.md](references/styles/analytical.md) |
| 科普视频口播（explainer-video） | 用口语讲清科学、历史或复杂机制，适合视频脚本和口播型长文 | [explainer-video.md](references/styles/explainer-video.md) |

只加载当前风格。

文章类型决定必须覆盖什么，风格决定如何讲，发布形式决定如何交付。例如「进化生物学解读＋科普视频口播＋视频脚本」。类型模板的次序和标题可按风格调整，但不能丢失证据、限制与适用条件。规则优先级：真实性与正确性 > 用户本次表达要求 > 所选风格 > 类型模板默认顺序。

## 默认工作流

1. 吃透用户提供的素材，确认受众、目的和核心问题。目标项目有读者或定位说明（如 `PRODUCT.md`、`README`、`AGENTS.md`）时先读，写下一句话：读者是谁，读完要能做什么。上下文足够时直接推进，不重复询问。
2. 判断哪些信息可能变化或需要精确引用。需要调研时优先使用官方文档、论文、源码和一手公告。论文或文档没说清的地方，先查代码、README 和 issue；能靠读代码回答的问题，不留给读者当「未核」。
3. 选择主风格并读取对应文件，形成一句核心判断，再设计结构。科普视频口播型可以先抛出问题，再沿因果链逐步建立解释。提纲阶段分配所选风格的强调额度，并标出支撑论点的数据图；不要正文写完再补图。
4. 根据文章类型选择结构，需要详细模板时读取 [references/article-structures.md](references/article-structures.md)。论文、技术报告和基准评测的解读用其中的「论文与研究解读」模板，不按原文章节顺序复述。开源项目的当前功能全景、版本更新、功能演进、方向观察和实践跟进，读取 [references/open-source-updates.md](references/open-source-updates.md)，按读者影响组织变化。
5. 配图是默认动作。短篇开源更新跟进按信息需要使用代码对照、表格或机制图，不设正文图片数量下限；目标项目要求的封面仍须提供。长篇仍遵守以下配图规则。长文至少配 3 张与论点直接相关的图片（新闻类配现场、人物、产品；研究类配原图、机制示意图、数据图），存入文章目录的 `assets/`（目标项目另有约定时按其约定）并逐张验证。**选图时逐张写一句「它支撑哪句话、哪个数字」——写不出就换图**；通用晶圆特写、无标识的办公楼、街景、纯 logo 这类装饰性照片在分析类长文里一律不用。科普视频口播稿默认交付口播文本，不要求配静态图片；用户需要分镜或画面建议时，单独标注镜头、屏幕文字与旁白，避免把画面说明混进朗读稿。

数据对比图的画法与渲染见 [references/gongzhong-publish.md](references/gongzhong-publish.md) 的「数据对比图」；来源、检索方法和图注规范见 [references/web-images.md](references/web-images.md)。
6. 完成初稿后按 [references/editorial-checklist.md](references/editorial-checklist.md) 逐遍自检，其中推理遍和一致性遍不能省；再用 `python3 <本 Skill 目录>/assets/lint_article.py <文章.md> --style <风格标识>` 做兜底核对，把仍超额的项改回事实陈述或具体判断。
7. 用户指定目标仓库或发布平台时，先读取并遵守该目标的 `AGENTS.md`、front matter、资源和验证约定。写作风格和文章类型的方法由本 Skill 提供；文件组织、选题范围、新建或更新策略，以及具体项目的历史追踪状态由目标项目提供。不要把某个项目的版本、检查日期或待研究事项写入本 Skill。

## 共用可读性与检查边界

表格用于比较，一般不超过 4 列；完整数据链接原表。散文一行出现超过 10 个数字时检查是否需要删减或改表格。代码、命令和配置用代码块承载，技术名词首次出现时给必要解释。图注只写读者需要的信息，处理过程留给交付说明。

lint 只识别可计数问题，不能证明事实已核实。所有风格都会检查人设词、宽表格、数字墙、报告套话、逐条给原作者打分和图注处理过程。表态频率的计数提示只对同行拆解风格启用；连续单句段提示对科普视频口播风格关闭；转述式开场钩子只提示同行拆解。真实经历命中人设词时，先人工确认来源，再使用 `<!-- lint-ok -->`；该标记会跳过整行检查，不能用来掩盖超额。

## 品牌视觉：封面与标题

默认使用 **蓝色大写 Z＋黑色小写 ata 的手写签名标识、番茄红与蛋黄黄的手写标题、黑灰简笔画或草稿素描背景**。封面要让人一眼看出本期主题；人物不默认沿用动漫设定。生成封面或设计标题视觉时读取 [references/brand-visual.md](references/brand-visual.md)，复用其中的选定参考图。用户本次指定的风格优先。

文章封面与视频封面分别保存；本技能维护文章封面及品牌视觉，视频平台的比例、适配与上传要求由视频制作和发布流程维护。

## 交付要求

- 直接交付完整文章或写入用户指定位置，不只给提纲，除非用户只要求提纲。
- 正文中的引用紧贴对应事实，优先链接到原始来源。
- 不虚构作者经历。缺少第一手材料时，用研究和推理支撑文章，不伪装成亲测。
- 如无法完成构建、渲染或事实核验，明确披露未验证项。
- 验证过程（逐格核对、裁图、哪些没核）写进交付说明。文末出处只列来源和读者需要知道的证据等级，不写成验证日志；图注同理。
- 改稿后同步重建全部已产出的派生文件（公众号版 `_公众号版.html`、剪贴板版 `_剪贴板版.html`、网页版等），避免旧派生文件静默过期。剪贴板版用 `./gzh_build/copy.sh 文章名 --no-copy` 重建：公众号版会顺带重建，用户的剪贴板不会被覆盖。
- 不附带冗长的写作过程说明；交付时简要说明文件位置、覆盖范围、验证结果和 lint 结果。

## 可选：发布到公众号

用户要求把成稿发布或排版到公众号时，读取 [references/gongzhong-publish.md](references/gongzhong-publish.md) 并按其流程执行：用 `assets/gzh_build/` 中的构建脚本和主题样式，把 Markdown 转成可直接粘贴进公众号后台的 HTML，挑选金句做荧光高亮，**把 `assets/brand/开头动画.gif` 复制到文章图片目录**（构建脚本会自动插到标题块下面，不需要在 md 里手写），用无头 Chrome 截图验证排版，封面按 [品牌视觉规范](references/brand-visual.md) 生成，复用蓝 Z 黑 ata 签名、红黄手写标题与主题素描背景，并向用户说明平台限制：手动粘贴后要逐张确认图片已转存（API 推送时图片已由接口上传），正文外链不可点。

## 可选：生成网页版文章

用户要求「出个网页版」「做成可分享的 HTML 长文」「网页文章」时，一律读取 [references/web-publish.md](references/web-publish.md) 并按其流程执行：用 `assets/gzh_build/` 中的 `build_web.sh`、`style_web.html`、`postprocess_web.py` 走 pandoc 管线，产出媒体报道质感的单文件 HTML（封面 + 双形态目录 + 编号正文 + base64 内联图片），无头 Chrome 截图验证。该路线与公众号路线独立，外链保持可点，**正文不插品牌动画 GIF**（封面已有 kicker 和落款，那是公众号版专属）。

**硬约束：网页版只交付文章目录里的一个静态 `.html` 文件。** 构建零依赖（pandoc + python3），禁止为网页版请求搭建任何工程化脚手架：不跑 npm/node，不建 React/Vite/TypeScript 工程，不产生 `package.json`、`node_modules`、tsconfig 等依赖文件，也不改用需要装依赖或搭脚手架的其他 Skill（如 beautiful-article）。2026-09-10 曾因改走脚手架路线在用户项目里留下整套 node 工程文件，被要求把整个目录删除返工。

## 维护：Skill 本体的修改与部署

本 Skill 的源头是模板仓库 `~/code/zata_code_template/skills/zata-writer`（下称仓库副本）；各 AI 工具加载的 `~/.xxx/skills/zata-writer` 等目录（下称安装副本）只是部署产物，没有版本控制。

**修改一律落在仓库副本，不要直接改安装副本。** 直接改安装副本会让两处分叉，之后任何方向的同步都可能把改动静默覆盖：2026-09-09 的两次事故（过期的安装副本把仓库刚补的 121 行实测结论抹掉；仓库里的旧措辞被抢在复核前提交进历史）都源于编辑面装反。

对 Skill 本体做任何修改（SKILL.md、references/、assets/ 的新增或改动）后，完成两件事：

1. **更新 description 里的时间戳**：front matter 的 `description` 以 `[Updated YYYY-MM-DD]` 开头，每次修改都把它改成当天日期（与 code-reviewer、idea-inbox 等 Skill 的约定一致），方便在 Skill 列表里一眼看出新旧。
2. **部署到各安装副本**。在模板仓库根目录执行：

   ```bash
   ./scripts/sync_template.sh --skill zata-writer
   ```

   非交互、只更新已安装该 Skill 的本机目录（~/.claude、~/.codex、~/.qoder-cn、~/.pi、~/.kimi-code、~/.codebuddy），不会在任何工具里凭空创建安装目录；首次装到新工具用交互式的 `just sync-local-skills`（fzf 逐项预览 diff）。提交前想先在安装副本上验证改动，可以提前部署，但仓库侧的提交始终由用户复核后决定。

**不要把安装副本同步回仓库。** `assets/sync_upstream.sh` 仅作急救保留：只有安装副本被直接改过、需要把改动抢救回仓库时才用它。它把无版本控制的副本单向覆盖进 Git 仓库——脚本守卫能挡住文件删除，挡不住仓库已提交内容被旧副本盖回，用完必须人工逐行复核 diff 再决定提交。

交付时向用户确认时间戳已更新、部署已执行。
