# Demo：让人看到接入后的效果

文档说“怎么接”，demo 说“接完是什么样”。两者缺一，读者要么不敢动手，要么接完发现和想的不一样。

## 先判断需要哪一种

| 类型 | 给谁 | 怎么看 | 成本与风险 |
|---|---|---|---|
| **A. 参考接入（可运行）** | 要接入的开发者 | 本地跑一个极小的“宿主系统”，真实引入你的 SDK / 脚本 | 低。需要读者有凭据与可访问的服务 |
| **B. 在线 demo（可点）** | 评估、售前、产品、不想装环境的人 | 打开一个 URL 就能操作 | 中到高。要自己托管一个会调用真实后端的东西，见下方安全规则 |
| **C. 录屏/截图（只看）** | 所有人 | GIF、视频、带标注的截图嵌进帮助文章 | 最低，但不能交互，且会过时 |

默认先做 **A + C**：A 保证接入路径真的可行，C 让只想看效果的人 30 秒内看懂。只有明确需要“别人不装任何东西就能点”时才做 B。

## 做 A：参考接入

- 放在仓库 `examples/<名称>/`，只有一个页面和一个极小的服务端。**页面里的接入代码要与帮助文章里的代码一字不差**，让读者对着看。
- 凭据只存在服务端（环境变量），页面里看不到；README 写清所需环境变量、启动命令、打开地址。
- 页面做成一个**像样的业务页**（例如一张待审批表），而不是空白页，这样读者能看出助手在真实页面里的样子，以及“选中文字作为上下文”这类和宿主页面交互的能力。
- 在文章里写明：demo 不能直接给别人用——它需要他们自己的凭据。

## 做 B：在线 demo

在线 demo 的本质是一个**对公网开放、会用你的凭据调用真实后端的入口**。这和“文档页面”的安全等级完全不同，先过这几条再动手：

1. **专用凭据。** 单独建一个 demo 租户/组织与专用密钥，不用任何生产密钥；权限与可见数据最小化，里面不放真实业务数据。
2. **凭据只在服务端。** 浏览器拿到的只能是短时效、一次性的东西（票据/令牌），不能是密钥。
3. **限速与配额。** 匿名访问者每人每天能发多少请求、总预算多少，要有上限；超限给出明确提示，而不是静默失败或一直烧钱。
4. **可随时吊销。** 能一键停用 demo 凭据；吊销后页面给出“demo 暂不可用”，不报错栈。
5. **不要让匿名访问者换取比 demo 更大的权限。** 例如 demo 的票据接口不能接受调用方指定任意用户 ID。
6. **明确标注。** 页面顶部写“演示环境，不要输入真实数据”。
7. **别把它藏在帮助中心里当作“文档”。** 它是一个有成本、有风险的服务，应有 owner、监控与下线条件。

做不到上面几条，就退回 A + C，不要硬上 B。

## 做 C：录屏与截图

- 嵌进帮助文章里，放在“接入步骤”之前或之后，回答“接完长这样”。
- 截图必须来自真实运行的页面，并标注环境与日期；录屏不能嵌入 Markdown 时，放链接。
- 会随界面改版过时。在文章的变更清单里加一条“界面变化时更新 demo 截图”。

## 与文档同步

- demo 与文章用同一段接入代码。改了属性、接口或状态码，demo 和文章一起改。
- 可以加一个最小检查：构建或测试时核对 demo 页面里的 `<script …>` 片段与文章里的片段一致；做不到自动就写进评审清单。
- demo 是文档的一部分：**部署后确认 demo 链接能打开**，和确认 `/llms.txt` 非空一样要做。
