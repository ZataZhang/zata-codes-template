# Readable HTML

## Overview

产出一份**给人读、能直接转发**的说明页。读者不在对话里，打开页面就要能看懂：结论在哪、为什么、下一步做什么。

所有页面类型共用一套东西：

- **设计令牌与组件**：`scripts/svg_kit.py` 里的 CSS（浅色、跟随系统的深色、显式深色三套）、SVG 组件、页面外壳。
- **通用规则**：下文的「通用原则」「视觉约定」「写作约定」。
- **工作流程**：写生成脚本 → 生成 → 校验 → 交付。

每种页面类型的结构不同，开始前先读对应的配方：

| 页面类型 | 典型请求 | 配方 |
|---|---|---|
| 架构说明 | 技术架构与可行性、平台规划、中台方案、系统设计 | `references/architecture.md` |
| 流程说明 | 某个角色一整套怎么操作、业务怎么流转、操作手册、上手指南 | `references/process.md` |
| 方案对比与决策建议 | 几个方案怎么选、技术选型、要不要做、给老板的建议 | `references/proposal.md` |
| 复盘与汇报 | 事故复盘、项目复盘、周报 / 月报 / 阶段汇报、调研结论 | `references/report.md` |

一份页面跨两类时（例如「架构 + 业务流程」），以主类型的配方为骨架，把另一类的节按其配方顺序接在后面，中间用分部标题（`Section.part`）隔开。

## 通用原则

这些规则来自读者对真实页面的修改意见，所有类型都适用：

1. **结论先行。** 页头用一句话定位：这是什么、给谁用、结论或建议是什么。读者只看页头也能拿走要点。
2. **先讲结构，再讲过程。** 先让读者知道东西是怎么组成的，再讲它怎么运转。架构先于业务流程，现状先于方案，结论先于经过。
3. **图文并重。** 纯文字没人看，只有图又看不懂。每张图上方用一句 `lead` 说明这张图回答什么问题；图下用表格、步骤列表或卡片补上图里放不下的细节。
4. **只放读者需要的信息。** 不在图上放「已有 / 新增 / 部分」这类内部进度角标；表格只写该写的列，比如层的职责就只写职责。内部状态如果确实重要，单独放进「实施路线」或「下一步」一节。
5. **起点不是边界。** 内容从一个场景、一个团队或一个案例切入时，要说清它只是第一个落地点，并说明怎么推广到其他场景。
6. **区分事实、判断和建议。** 现状写成事实并注明依据；推断和建议明确标出来。页脚写清依据的来源和版本，以及哪些内容没有经过验证。

## 视觉约定

**颜色按语义编码**，同一种颜色在一份页面的所有图里含义相同。方框种类见 `svg_kit.KINDS`：

| 种类 | 颜色 | 默认语义 |
|---|---|---|
| `agent` / `agentband` | 蓝 | Agent、自动化、系统产出 |
| `files` / `fileslite` | 青绿 | 工作态、草稿、进行中 |
| `kn` / `knstrong` | 紫 | 正式资产、已发布、结果；`knstrong` 标出沉淀点 |
| `biz` | 橙 | 外部系统、实时事实；在复盘和时间线里表示异常 |
| `gate` / `gateband` / `gatebox` / `gatelite` | 深蓝 | 权限、闸门、确认、关键决策；深色种类文字自动反白 |
| `plain` / `ghost` / `start` | 中性 / 虚线 / 强调 | 人和通用组件 / 不参与或未来项 / 当前焦点（每张图最多一处） |

不是架构类页面时，可以重新定义这几种颜色的语义，但要在图例里写明（`legend({...})`），并且一份页面里保持一致。

**页面组件**（CSS 类，HTML 直接用）：

| 组件 | 类名 | 用于 |
|---|---|---|
| 原则 / 要点卡片 | `.principles` > `div` > `b` + `p` | 4-6 条并列要点 |
| 结论条 | `.verdict` > `b` + `p` | 决策建议、复盘结论，一页最多一处 |
| 方案卡片 | `.options` > `.opt`（推荐项加 `.rec`） | 并列方案比较 |
| 指标卡片 | `.metrics` > `div` > `b` | 衡量指标、关键数字 |
| 示例卡片 | `.card` > `dl` | 展示一条数据实际带哪些字段 |
| 表格 | `.tbl` > `table` | 维度对比、矩阵、路线 |
| 提示 | `.note` | 边界说明、注意事项 |
| 标签 | `.chip.c-ok` / `.c-warn` / `.c-info` | 表格里的状态（如「直接执行 / 需要确认」） |
| 两栏 | `.two` | 左说明右示例，窄屏自动单栏 |

**SVG 组件**：`band`（分层）、`box`（方框）、`arrow`（连线）、`fan` / `merge`（一对多扇出、多对一汇聚）、`swimlane`（阶段 × 角色泳道）、`timeline`（横向时间线）、`label`（连线旁说明）。用法见 `svg_kit.py` 的 docstring。

**尺寸与文字**（超出就会重叠，这是最常见的问题）：

- viewBox 宽 1200（泳道图 1300），窄屏下横向滚动，不缩小文字。
- `box` 标题 13.5px，中文约 14px/字：186px 宽的框标题不超过 11 个字，说明行（11.5px）不超过 14 个字。说明行不会自动换行，太长就拆行或缩短。
- `band` 左侧留 160-180px 写层名，子框从 `x+180` 开始。
- 泳道单元格 176×70，时间线卡片 172×78：标题不超过 11 个字，说明行最多 2 条。
- 方框之间留至少 12px 间距，箭头起止点落在方框边缘。主流程箭头用强调色实线；引用、回流用 `dash=True`；次要关系用 `accent=False`。

**主题**：所有颜色都经由 CSS 令牌。新增颜色时，浅色、跟随系统的深色、显式深色三处都要加，组件里不写死色值。

## 写作约定

- 用户可见文案默认中文，写给不在对话里的读者；术语第一次出现时用一句话解释。
- 一句话说一件事。不用「不是 X，而是 Y」句式，不用破折号插入语，不用「值得注意的是」这类套话。
- 图里只放名词短语和极短的说明，完整解释放在图下。
- 页面要能单独读懂：不写「如上所述」「按之前讨论」「你提到的」。
- `<title>` 写成 2-4 个词的名字，不加冒号或破折号后的解释。
- 引用仓库内容时写相对路径和版本（例如 `main @ 30c336b0`）。
- 公开仓库或要对外分享的页面，不写客户名、内部系统名、个人信息和敏感业务数据。

## Workflow

### 1. 定类型、收事实

判断页面类型，读对应的 `references/*.md`。收集事实：相关文档、源码、数据、用户给的图片。记下哪些是现状、哪些是建议，写页面时不能把建议说成已实现。

### 2. 写生成脚本

在临时目录写生成脚本（会话 scratchpad 或 `/tmp`，**不写进被讲解的仓库**）：

```python
import sys
sys.path.insert(0, "<本 skill 目录>/scripts")
from svg_kit import Lane, Section, arrow, band, box, fan, label, legend, merge, page, svg, swimlane, timeline
```

每张图一段代码，返回 `svg(...)`；每节组装成 `Section(anchor, nav, html, part)`；最后用 `page(...)` 拼成整页写盘。运行 `python scripts/svg_kit.py --demo /tmp/readable-demo.html` 可以看到所有组件的示例。

改内容时改生成脚本再重新生成，不要手改产出的 HTML，否则下次生成会被覆盖。

### 3. 校验

```bash
# 每个 SVG 必须是合法 XML（未转义的 & 或 < 会让整张图消失）
python3 -c "
import re,sys,xml.dom.minidom
s=open(sys.argv[1],encoding='utf-8').read()
[xml.dom.minidom.parseString(m.group(0)) for m in re.finditer(r'<svg.*?</svg>',s,re.S)]
print('svg ok')" <输出.html>

# 整页截图（片段输出时先在前面补 <!doctype html><meta charset="utf-8">）
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless=new --disable-gpu \
  --window-size=1300,5200 --screenshot=/tmp/shot.png file://<输出.html>
```

自己看一遍截图，重点检查最长的标题是否溢出方框、方框是否重叠、箭头是否指对。看一次、修一轮，不反复截图。

### 4. 交付

- 本地打开：`page(standalone=True)`，然后 `open <输出.html>`。
- 发布到会自动包外壳的平台（如 claude.ai Artifact）：`page(standalone=False)` 只输出片段。
- 用户要修改时改生成脚本、重新生成，保持同一个输出路径，已发布的链接就不会变。
- 除非用户明确要求，不为页面改动提交到任何仓库。
