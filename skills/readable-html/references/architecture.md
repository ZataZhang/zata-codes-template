# 配方：架构说明

适用：技术架构与可行性、平台规划、中台方案、系统设计、模块边界说明。

读者想知道：这套东西由哪些部分组成、各自负责什么、关键过程怎么走、数据和权限怎么管、先做什么后做什么。

## 结构

| 部分 | 节 | 用什么表达 |
|---|---|---|
| 页头 | eyebrow + h1 + 定位陈述 + 目录 | 定位：这是什么、首先给谁用、从哪个场景切入 |
| 第一部分 · 架构设计 | 设计原则 | `.principles` 4-6 张卡片，粗体结论 + 两三句解释 |
| | 分层架构 | `band` 分层图 + `legend()` + 「层 / 职责 / 包含」三列表 + `.note` 写部署边界（例如不新增独立服务） |
| | 关键调用过程 | `fan` / `merge` 流程图，展示一次请求从进入到产出；再配对比表或边界表（例如人 vs Agent、哪些动作需要人确认） |
| | 数据模型 | 类型表 + `.card` 示例，展示一条数据实际带哪些字段 |
| | 生命周期 | 横向流程图 + 「维度 / 各类数据」对比表 |
| | 权限 | 「∩」交集图（几个条件框 + `label(..., "∩", css_class="t-h")`）+ 需要新增的实体表 |
| 第二部分 · 业务流程 | 按 `process.md` 的结构 | 泳道图、协作流转、扩展到其他场景 |
| 收尾 | 实施路线 | 「阶段 / 交付内容 / 完成标志」表 + 实施前需要确定的问题 |
| 页脚 | 依据与限制 | 依据的源码版本与文档；哪些判断来自阅读而非运行验证 |

## 要点

- 分层图从上到下：使用者 → 场景 / 应用 → 运行时 → 关键中间层（权限、网关）→ 数据 → 存储。最关键的一层用 `gateband` 深色突出，每张图只突出一层。
- 「层 / 职责 / 包含」表的「包含」列与图里的方框一一对应，不写现状差距。
- 现状和建议要分开写：现状引用具体路径，建议写成「需要」「建议」。差距汇总放在实施路线里。
- 起点场景要单列一节「扩展到其他场景」，用「场景 / 新增什么 / 复用什么」表说明底座如何复用。
